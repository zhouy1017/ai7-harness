# Current handoff

Begin by identifying your harness, Codex or Claude Code, then query the [Dispatch Register](docs/agents/dispatch-register.md): read the current Issue bodies and Launch/Return Receipts, then correlate them with your own harness's live session state, with `ListAgents` in your own session for any subagent attempt, and with your own background-process tools for any `cli-session` attempt. Do not infer completion from `idle` or a process exit, and do not copy transient session status into this router.

Dispatch follows [ADR 0061](docs/adr/0061-route-repository-dispatch-by-commander-harness.md) and [ADR 0063](docs/adr/0063-allow-cross-harness-dispatch-through-cli-launched-task-sessions.md): you select each attempt's harness and launch mode. A same-harness attempt is a fresh Task Session in its own worktree launched as a hand-created top-level session, as a Claude Code subagent through your Agent tool (`run_in_background: true`, `isolation: "worktree"`, explicit class alias `sonnet`/`opus`/`fable`; effort inherits your session), or as a `cli-session`. A cross-harness attempt is a `cli-session` launched from your shell with the exact class model and effort, which needs the target harness's CLI callable from your own shell; both CLIs are installed host-wide as global npm packages and logged in, and each Commander verifies the target CLI from its own shell before a cross-harness launch because packaged desktop apps virtualize `%APPDATA%`. Every body carries both binding lines; receipts are schema v4 with `commander_harness`, `harness`, `launch_mode`, and `agent_id`; the commit trailer follows the attempt's harness. In the `subagent` and `cli-session` modes you launch, relay, and audit only; never edit the attempt's worktree or branch. A `subagent` preflight leaves one untracked `.ai7-preflight-<dispatch_id>` marker at the worktree root, deleted by the Worker after it verifies its Launch Receipt.

Development verification follows [ADR 0062](docs/adr/0062-adopt-a-local-verification-ladder-with-ci-as-delivery-gate.md) and the [CI and test boundary](docs/agents/ci-test-boundaries.md): the Local Verification Ladder is complete and required before Ready (`doctor`, `bootstrap`, `check`, `test`, `test:service`, `build`, the admitted Journeys through `e2e` / `e2e:all`, and the full-fidelity `e2e:debug` / `e2e:repeat`), and the Hosted E2E Functional Gate stays the unchanged per-Ready-pull-request delivery gate; a red Gate returns to Draft for local, then CI-parity, reproduction. The Windows-only J-02 restart failure is fixed at the product (#239 / PR #245: bounded terminal-version store-truth validation and a 120 s startup readiness deadline), and its runner-side classifications and a shared browser-disconnect guard and CDP deadline helper across the six E2E runners have since landed.
