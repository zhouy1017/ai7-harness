# Compose the full Harness engine behind a narrow tool surface

Status: **accepted; its absolute Agent Data Root enforcement claim is unproven and reopened by ADR 0027**

AI7 composes the complete Harness behavior engine — planning, context assembly, tool pipeline, subagents, workflows, sessions, replay, and snapshots — while an editorial Run never receives the generic coding-agent tool surface of shell, roaming filesystem, and arbitrary network. "Full capability" and least privilege conflict only when the engine is confused with the tool surface. The governing reason is the user: a literature professional cannot assess whether a proposed action is safe, so the product must never ask them to authorize one. Capability decisions belong to AI7's composition rather than to a runtime prompt that delegates expert judgment to someone without the basis to exercise it, and every capability an editor sees is expressed in editorial terms rather than in processes, paths, or endpoints.

This is not the absence of filesystem and network access. Import and export exist as bounded capabilities over a user-chosen file or destination, and authorized external research exists as a provenance-bearing capability, both enforced at the Harness tool guard and the AI7 service facade. This ADR intended an AI7-owned Agent Data Root to be an outer OS filesystem boundary, with a per-Run unscoped scratch area for temporary work, while Run Source Scope prevents a Run scoped to one Book from reading another's manuscript. The available reference mechanisms do not yet prove that promise: Harness Windows ACL confinement is partial, and its macOS Seatbelt profile governs file writes but not reads, networking, or process visibility. Until ADR 0027's platform work accepts and verifies a mechanism—or explicitly revises the guarantee—the capability/service facade is the only accepted enforceable product boundary and the OS boundary must be described as intended rather than enforced. The Protected Secret Store stays outside the root, and the root itself stays outside every repository working tree.

Two capability profiles exist. The Editorial Capability Profile ships and exposes domain capabilities only. The Developer Capability Profile carries the generic tool surface, is what repository development workers run under, and is a build artifact rather than a settings toggle — a user cannot escalate into it, because a self-service escalation path would hand the expert judgment back to the person who cannot exercise it. Users nonetheless retain complete access to their own material: they work with Books, sources, and deliverables rather than paths, and retrievability of every imported source and generated deliverable is a guarantee, so that freedom from filesystem literacy never becomes an opaque store the work cannot leave. A middle power-user profile is deferred until a named workflow requires one.
