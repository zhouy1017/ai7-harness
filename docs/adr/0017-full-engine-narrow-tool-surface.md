# Compose the full Harness engine behind a narrow tool surface

AI7 composes the complete required Harness behavior engine — the generic turn loop, planning, context assembly, tool pipeline, policy/composition seams, Sessions, and subagents where needed — while an editorial Run never receives the generic coding-agent tool surface of shell, roaming filesystem, and arbitrary network. "Full engine" means the complete behavior/composition capability AI7 needs, never the full Harness package set. Harness `schedule`, `jobs`, and workflow packages are excluded from the selected subset: AI7 owns which Runs exist and every durable editorial Workflow Instance, while DSH converses inside an AI7-authorized execution. Upstream replay or snapshot support may be inspected or used only inside a later exact journey or diagnosis; it is not an admitted standing proof programme. "Full capability" and least privilege conflict only when the engine is confused with the tool surface. The governing reason is the user: a literature professional cannot assess whether a proposed action is safe, so the product must never ask them to authorize one. Capability decisions belong to AI7's composition rather than to a runtime prompt that delegates expert judgment to someone without the basis to exercise it, and every capability an editor sees is expressed in editorial terms rather than in processes, paths, or endpoints.

This is not the absence of filesystem and network access. Import and export exist as bounded capabilities over a user-chosen file or destination, and authorized external research exists as a provenance-bearing capability, both enforced at the Harness tool guard and the AI7 service facade. The Agent Data Root is the intended platform filesystem boundary, with a per-Run unscoped scratch area for temporary work, but neither Windows nor macOS is assumed to provide whole-process confinement until its concrete mechanism supports that claim. The AI7 capability and service facades are the enforceable boundary; Run Source Scope separately stops a Run scoped to one Book from reading another's manuscript. A data root holds every Book, so raw access across it would silently regress the scope model even if native OS restrictions exist. The Protected Secret Store sits outside the root, and the root itself lives outside any repository working tree so that manuscripts cannot reach a commit even by accident.

Two capability profiles exist. The Editorial Capability Profile ships and exposes domain capabilities only. The Developer Capability Profile carries the generic tool surface, is what repository development workers run under, and is a build artifact rather than a settings toggle — a user cannot escalate into it, because a self-service escalation path would hand the expert judgment back to the person who cannot exercise it. Users nonetheless retain complete access to their own material: they work with Books, sources, and deliverables rather than paths, and retrievability of every imported source and generated deliverable is a guarantee, so that freedom from filesystem literacy never becomes an opaque store the work cannot leave. A middle power-user profile is deferred until a named workflow requires one.

## Later partial supersession

[ADR 0045](./0045-preserve-native-dsh-artifacts-behind-ai7-authority-sidecars.md) partially supersedes this ADR only where the earlier artifact/composition boundary did not admit product-managed native DSH artifact acquisition and scoped enablement. Those lifecycle operations may now exist behind the same AI7 boundary. This does not admit DSH `schedule`, `jobs` or workflow packages, add a generic install tool to model-visible editorial Runs, widen the narrow tool surface, change AI7 ownership of Runs or durable Workflow Instances, or create a self-service capability-profile escalation; every other obligation in this ADR remains in force.
