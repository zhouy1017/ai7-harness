# Ship a TypeScript-only runtime with no embedded Python

AI7 is TypeScript and Node throughout, and no Python interpreter ships with the product. The audit of the predecessor removed the reason to keep one: its 62 Python files carry zero third-party dependencies — no `requirements.txt`, no `python-docx`, no PDF library — and handle DOCX with `zipfile` and `xml.etree`, treating it as the zip of XML it is. Python was the backend implementation language rather than a document-processing capability, and the packaged interpreter existed only to ship that backend. Every capability in it has a direct Node equivalent, mostly stdlib to stdlib: a zip library and an XML parser for OOXML, `node:crypto` for hashing, and the Credential Broker over Windows Credential Manager in place of `ctypes` into DPAPI.

Three accepted decisions already pointed the same way. The upstream package family is TypeScript ESM on Node `^22.19.0 || >=24`, a second runtime would contend with the single-execution-authority rule, and ADR 0006 accepted manuscript semantics while explicitly rejecting the legacy Python and JSON-store machinery — so the business logic is re-expressed from contract regardless. Keeping Python would therefore port nothing while carrying roughly 50 to 100 MB in a portable build, a second dependency tree, a second security surface, a second upgrade contract, cross-language IPC, and the standing risk about Python runtime limitations on Windows. Direct OOXML control in TypeScript is also better suited to the round-trip fidelity the Standalone editing obligation requires than a library's intermediate document model.

The trigger for reconsideration is narrow. A named capability with no adequate Node implementation may enter as a bounded native module or a sidecar process under its own ADR; it never enters as a general-purpose embedded interpreter, and "we might need scripting" is not a qualifying reason. PDF import is greenfield in either language, since no library-backed PDF implementation existed at the audited pin, and it is covered in Node by `pdfjs-dist` rather than forcing Python back into the product.
