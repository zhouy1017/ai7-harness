# Allow cross-harness dispatch through CLI-launched Task Sessions

On 2026-09-04 the Owner decided that a Commander may dispatch a Worker or Reviewer attempt to either harness regardless of its own: a Claude Code Commander may launch a Codex `gpt-5.6-luna @ medium` T1 attempt, and a Codex Commander may launch a Claude Code `claude-opus-5 @ high` T2 attempt. Neither desktop harness can create, observe, or message the other's sessions—Claude Code has no `create_thread`, `list_threads`, or `send_message_to_thread`, and Codex has no `list_sessions`, `send_message`, or Agent tool—so a cross-harness attempt runs as a **CLI-launched Task Session** that the Commander starts from its own shell. This supersedes [ADR 0061](./0061-route-repository-dispatch-by-commander-harness.md)'s harness-routing clauses (the Commander's harness selecting the route, one attempt never mixing harnesses, a Reviewer sharing the Commander's harness, and its second rejected alternative), reverses the "no CLI launcher" rule of ADR 0059, ADR 0060, and ADR 0061 for this launch mode only, and rebinds the commit trailer to the attempt's own harness. Fixed bindings, the one-binding-line-per-harness Issue body, the two-stage launch, immutable receipts, no fallback, bounded parallelism, serial integration, the three state namespaces, and Commander-only integration and external actions continue unchanged.

## Decision

The Commander selects the attempt's `harness`, `codex` or `claude-code`, per attempt and independently of its own `commander_harness`. The attempt's harness selects the Issue body's requested-binding line and the fixed class binding; the Issue body still needs no change. A Reviewer's harness is selected per attempt in the same way and may differ from the Worker's harness and from the Commander's, which strengthens rather than weakens fresh-context independence.

Launch modes are keyed by harness pair. A same-harness attempt may use the harness's native modes—`top-level-session` on both harnesses, `subagent` on Claude Code—or `cli-session`. A cross-harness attempt uses `cli-session` only, because the native modes depend on session tools the Commander does not have. Whichever mode is used, the attempt remains one fresh Task Session in its own worktree with one Launch Receipt.

In the **`cli-session`** mode the Commander runs the target harness's CLI in the background from its own shell, with the first prompt as the CLI's prompt, and continues the session by resuming it with the finalized Receipt permalink. For a Claude Code target: `claude -p "<first prompt>" --model <exact model> --effort <effort> --worktree <name> --output-format json`, run from the main checkout; the JSON result's `session_id` is the Task Session ID, the CLI creates `.claude/worktrees/<name>` on a generated branch, and follow-ups are `claude -p "<message>" --resume <session_id>` run from the worktree. For a Codex target: the Commander first creates the worktree itself with `git worktree add --detach <path> <exact start>`, then runs `codex exec "<first prompt>" -m <exact model> -c model_reasoning_effort=<effort> -C <path> --sandbox workspace-write --json -o <report file>` (a Reviewer gets `--sandbox read-only`); the `thread.started` event's `thread_id` is the Task Session ID, and follow-ups are `codex exec resume <thread_id> "<message>" -C <path>`. Both CLIs accept the exact model and effort, so a `cli-session` attempt carries the full class binding; `launch_accepted_binding` records the CLI arguments as sent plus the CLI's start event when it reports a model, labeled as such and still not proof of the effective runtime model. A Worker receives the permission mode and tool allowlist its brief's validation needs and nothing broader; a Reviewer receives a read-only allowlist and no edit tools. `--bare`, `--ephemeral`, `--dangerously-bypass-approvals-and-sandbox`, and `--approve-for-me` are never used.

The CLI is an Owner host prerequisite, never a repository dependency, launcher script, daemon, or connector. The official global npm packages, `@anthropic-ai/claude-code` and `@openai/codex` with its `win32-x64` platform alias, land in the `%APPDATA%\npm` directory that is already on the user PATH, and both CLIs share the desktop apps' existing logins. Both desktop apps are packaged Windows apps that virtualize `%APPDATA%`, so a CLI installed from inside one app's session is visible only to that app's sessions; the host-wide install is performed once from an unpackaged terminal, and every Commander verifies the target CLI from its own shell before launching. The repository records the prerequisite, not the installation. Where the target harness's CLI is not callable, a cross-harness attempt records `launch-unavailable`.

Receipts use schema v4 with `commander_harness` beside the attempt's `harness`, `launch_mode` (`top-level-session | subagent | cli-session`), and `agent_id`. A `cli-session` attempt's live status is `running | idle | ended`, read from the CLI process: alive, exited after a turn and resumable, or unresumable or killed; if the target desktop app also shows the session, the Owner-observed raw value is retained beside it. Agent-authored commits carry the trailer of the attempt's own harness—`Co-authored-by: OpenAI Codex <codex@openai.com>` for a Codex attempt, `Co-Authored-By: Claude <noreply@anthropic.com>` for a Claude Code attempt—so a trailer names the authoring harness, never the Commander's and never a model.

The Dispatch Register stays a live query. A Commander reads its own harness's session tools for native-mode attempts, its own background-process and agent tools for `cli-session` and `subagent` attempts, and receipts for everything else; it never claims live state for the other harness's desktop sessions. Worktree rules follow the mode: `claude --worktree` derives its start from the harness's worktree base setting and may remove an unchanged worktree at exit, so step 4 of the two-stage launch verifies the worktree and enforces the exact start; a Codex `cli-session` worktree is created by the Commander at the exact start. The detailed contract lives in [Repository Development Dispatch](../../kick-in/27-repository-development-dispatch.md) and [Dispatch Register](../agents/dispatch-register.md).

## Rejected alternatives and consequences

- **Owner-attended hand-created session on the other harness with human relay.** Rejected by the Owner: it puts a person in the launch, follow-up, and report path of every cross-harness attempt; the CLI keeps launch, observation, and follow-up with the Commander.
- **Letting the Worker post its report to the Issue to shorten a relay.** Rejected: the Worker external-action boundary is unchanged; the Commander relays the CLI's final message into the Return Receipt.
- **Cross-harness launch through desktop session tools.** Impossible: neither harness exposes the other's session tools.
- **Cross-harness `subagent`.** Impossible: an Agent-tool subagent is always a Claude Code agent inside a Claude Code session.
- **A repository-managed CLI install, wrapper script, or launcher.** Rejected: the Commander invokes the CLI directly; the repository gains no dependency, script, daemon, or connector, and ADR 0027 gains no gate.
- **Bypassing sandbox or approvals for speed.** Rejected: a `cli-session` attempt gets exactly the permissions its brief's validation needs.

ADR 0061's harness-routing clauses and second rejected alternative are superseded; ADR 0060's fourth rejected alternative (CLI-launched sessions out of scope) is reversed for cross-harness dispatch. ADR 0061's launch modes, bindings, Issue-body contract, receipt schema, and every other clause continue. ADR 0027's earlier supersession of ADR 0015's verification and review-gate clauses remains historical; this decision revives no review, proof, model, exact-head, or CI gate.

This decision governs repository-development orchestration only. It changes no AI7 product Model Role, Provider Resolution Plan, Provider Preflight, Approved Fallback Chain, Provider Processing Policy, DSH subagent/artifact behavior, credentials, Effect, E2E provider-free boundary, export, publication, distribution, release, or `main` authority. The product-domain term Codex Interaction Model Reference under ADR 0041 is unaffected.
