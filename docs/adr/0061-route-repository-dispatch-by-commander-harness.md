# Route repository dispatch by the Commander's harness

On 2026-09-04 the Owner decided that repository development must work from both Codex and Claude Code, so the single-harness exclusivity of ADR 0059 (Codex-only) and ADR 0060 (Claude Code-only) is replaced by harness-conditional routing: the Commander's own harness selects the route for every Worker and Reviewer it launches. The Codex route restores ADR 0059's bindings, Task Session tooling, live-status values, and trailer; the Claude Code route continues ADR 0060's. Every other rule those decisions introduced—the Commander/Worker/Reviewer authority split, one-Issue/branch/pull-request/single-writer rule, Issue-body hash, two-stage launch, no fallback, bounded parallelism, serial integration, three state namespaces, validation lifecycle, and Commander-only integration/external actions—is inherited unchanged.

Later on 2026-09-04 the Owner reversed ADR 0060's first rejected alternative: on the Claude Code route the Commander may also launch a Worker or Reviewer attempt as an in-session subagent through its harness's Agent tool. The hand-created top-level session remains a launch mode. This revision adds the `subagent` launch mode, the receipt fields that identify it, and the effort-inheritance rule below. The same day, [ADR 0063](./0063-allow-cross-harness-dispatch-through-cli-launched-task-sessions.md) superseded this decision's harness-routing clauses—the Commander's harness selecting the route, one attempt never mixing harnesses, and a Reviewer sharing the Commander's harness—by letting the Commander select the attempt's harness per attempt and adding the `cli-session` launch mode. Those clauses remain below as history; every other clause continues.

## Decision

Two harnesses are supported: `codex` and `claude-code`. One attempt never mixes them: a Codex Commander launches Codex Task Sessions, a Claude Code Commander launches Claude Code Task Sessions, and a Reviewer runs on the same harness as the Commander at the reviewed class's binding. Cross-harness Worker or Reviewer attempts and any third harness are out of scope. (Superseded by ADR 0063: the attempt's harness is selected per attempt; a third harness remains out of scope.)

Bindings are fixed per harness. Codex: Commander `gpt-5.6-sol @ ultra`, T1 `gpt-5.6-luna @ medium`, T2 `gpt-5.6-terra @ high`, T3 `gpt-5.6-sol @ xhigh`. Claude Code: Commander `claude-fable-5-1 @ xhigh`, T1 `claude-sonnet-5 @ medium`, T2 `claude-opus-5 @ high`, T3 `claude-fable-5-1 @ xhigh`. There is no fallback across models, efforts, or harnesses.

The Issue body remains the canonical Change Brief and now carries one requested binding per harness, `Requested binding (codex)` and `Requested binding (claude-code)`, both frozen by the body hash, so a work-ready Issue is launchable from either Commander without a body change. A body that carries only a single legacy `Requested binding:` line binds only the harness of that model family; adding the other line is a material revision. The launching Commander records its `harness` and the selected line as `requested_binding`; the selected line and the launch-accepted binding must agree, or the attempt records `mismatch` and stops.

A **Task Session** is one fresh execution context of the Commander's harness with its own worktree, created in one of that harness's launch modes: on Codex, a Task Session created by `create_thread` with an app-managed worktree under `~/.codex/worktrees/<id>/ai7-harness`, observed through `list_threads`, `wait_threads`, and `read_thread`, messaged through `send_message_to_thread`, and retired through `set_thread_archived`; on Claude Code, either a desktop session created by hand with a `.claude/worktrees/<name>` worktree, observed through `list_sessions`, `get_session`, and `list_events`, messaged through `send_message`, titled through `set_session_title`, and retired through `archive_session`, or a subagent spawned by the Commander's Agent tool as described below. Read-only exploration subagents inside a Worker or Reviewer session may run only within that same worktree and never become a second writer or a separate attempt identity.

**Launch modes.** The Commander selects the launch mode at launch and the Launch Receipt records it as `launch_mode`; the Issue body does not need to select it, and a body line that names exactly one mode binds the attempt to that mode. Codex has one native mode, `top-level-session`. Claude Code has two: `top-level-session`, the hand-created desktop session, and `subagent`, in which the Commander calls its harness's Agent tool with `run_in_background: true`, `isolation: "worktree"`, an explicit `model` equal to the fixed class alias—`sonnet` for T1, `opus` for T2, `fable` for T3—and the first prompt as the call's `prompt`. The subagent starts cold with its own context and its own harness-created worktree under `.claude/worktrees/`, is continued through the harness's agent-message tool, and reports only to the Commander, which relays that report into the Return Receipt and never edits the attempt's worktree or branch itself. A subagent attempt is a Task Session for every rule of this decision: fresh context per attempt, one writer, role-specific start, two-stage launch, verified Receipt, no fallback, the Worker cap, and Reviewer read-only non-delegation, under which a Reviewer subagent spawns no agent. A subagent attempt is not visible in the desktop session list; its live state is observable only inside the hosting Commander session, and its durable evidence is its receipts. That cost is accepted. ADR 0063 adds the third mode, `cli-session`.

**Effort in the `subagent` mode.** The Agent tool call carries no effort parameter. This was verified on 2026-09-04 against the tool's parameter schema (`description`, `prompt`, `subagent_type`, `model`, `isolation`, `run_in_background`) and the Claude Code documentation, which allows an effort override only in a subagent definition file's frontmatter, an owner this decision does not introduce. A subagent attempt therefore inherits the Commander session's effort level, `xhigh` under the fixed Commander binding. The class model is enforced through the explicit alias; the class effort is not enforceable in this mode and is recorded as `inherited`. The effort component is excluded from the `mismatch` comparison and from a Reviewer's `class_match` in this mode; the alias comparison still applies, and an alias other than the fixed class alias is a `mismatch`.

Launch keeps ADR 0059's two-stage skeleton with harness-specific attach steps. The first prompt carries the immutable launch expectations and a no-write preflight. After that turn stops, the Commander verifies the launch-accepted binding and a clean checkout at the role-specific start (Worker exact base; Reviewer immutable `reviewed_head`), attaches only a Worker checkout to the Issue branch—on Codex by attaching the clean detached checkout to the pre-created branch, on Claude Code by resetting a clean checkout to the exact start when needed and renaming the harness-generated branch to the reserved Issue branch, in the `subagent` mode operating on the worktree path from the Commander session—posts the finalized Launch Receipt, and sends only its permalink through the harness's session or agent message tool. A Reviewer stays detached and read-only.

Receipts use schema v4, which keeps schema v3's `harness`, `session_id`, `client_thread_id`, `session_title`, `worktree_path`, `source_branch`, and per-harness live-status fields and adds `launch_mode`, `agent_id` (the identifier the Agent tool returned for a subagent attempt; `none` otherwise), and, under ADR 0063, `commander_harness`. In the `subagent` mode `session_id` is the hosting Commander session's ID, `session_title` records the Agent call's `description`, and live status is `running | idle | ended`. `launch_accepted_binding` is the harness's launch evidence—the accepted `create_thread` request on Codex, the desktop session metadata for a Claude Code top-level session, and, for a subagent, the Agent call parameters as the Commander sent them (`<alias> @ inherited`), labeled as call parameters because no harness-readable metadata exists for a subagent—and `reported_execution_binding` keeps its inference label; none is proof of the effective runtime model. Schema v1, v2, and v3 receipts remain historical evidence.

Agent-authored commits carry the stable product-level trailer of the Commander's harness: `Co-authored-by: OpenAI Codex <codex@openai.com>` on the Codex route or `Co-Authored-By: Claude <noreply@anthropic.com>` on the Claude Code route. A trailer never names a model. (ADR 0063 rebinds the trailer to the attempt's own harness.)

The Dispatch Register remains a live query over Issue receipts plus the Commander harness's built-in session tools and, for a subagent attempt, the hosting Commander session's agent listing, task output, and completion notifications; it adds no ledger, daemon, database, host connector, query script, workflow, or gate. Root `PROGRESS.md` and `HANDOFF.md` remain Commander-owned integration-line routers. The detailed contract lives in [Repository Development Dispatch](../../kick-in/27-repository-development-dispatch.md) and [Dispatch Register](../agents/dispatch-register.md).

## Rejected alternatives and consequences

- **Single-harness exclusivity** (ADR 0059's Codex-only and ADR 0060's Claude Code-only rules). Rejected: the Owner operates both harnesses, and an Issue written for one must remain launchable from the other without contradicting current authority.
- **Cross-harness Worker or Reviewer within one attempt.** Rejected here because receipts, session tools, live-status values, and trailers would mix; reversed by ADR 0063, which keeps them separate by recording the attempt's harness and the Commander's harness as distinct fields and by launching cross-harness attempts only through the target harness's CLI.
- **Class-only Issue bodies with bindings resolved at launch.** Rejected: the body must keep freezing the exact model and effort under the hash; two explicit lines preserve that while allowing either Commander to launch.
- **Automatic harness fallback.** Rejected: no fallback of any kind exists; an unavailable binding records `launch-unavailable`.
- **Keeping ADR 0060's rejection of in-session subagent attempts.** Reversed by the Owner on 2026-09-04. Its objections are answered by rule rather than by mode: the Commander launches, relays, and audits but never authors; each spawn starts cold in its own worktree, so contexts do not mix; the receipt's `launch_mode` and `agent_id` identify an attempt that the session list cannot show; and Reviewer non-delegation explicitly forbids a Reviewer subagent from spawning agents. The residual costs—no desktop session-list visibility, no per-call effort, a worktree the harness removes when unchanged, and a transcript that ends with its hosting session—are accepted and recorded.
- **Subagent-only Claude Code launch.** Rejected: the hand-created top-level session remains a launch mode; the Commander chooses per attempt.
- **Subagent definition files that pin per-class effort.** Not adopted: they would add a new controlled owner under `.claude/agents/` and require their own decision; until one exists, effort inherits.
- **Recording a subagent's model or effort as harness metadata.** Rejected: the Agent call accepts only a model alias and no effort, and nothing reads the resolved model back; the receipt records the parameters as sent and says so.

ADR 0060 is superseded in full and its first rejected alternative is reversed by this revision; ADR 0059's remaining exclusivity clause is superseded; all remain at their stable paths as history, and their route texts continue here. ADR 0027's earlier supersession of ADR 0015's verification and review-gate clauses remains historical; this decision revives no review, proof, model, exact-head, or CI gate.

This decision governs repository-development orchestration only. It changes no AI7 product Model Role, Provider Resolution Plan, Provider Preflight, Approved Fallback Chain, Provider Processing Policy, DSH subagent/artifact behavior, credentials, Effect, E2E provider-free boundary, export, publication, distribution, release, or `main` authority. The repository-development subagent of this decision is a Claude Code Agent-tool subagent and never a DSH subagent. The product-domain term Codex Interaction Model Reference under ADR 0041 is unaffected.
