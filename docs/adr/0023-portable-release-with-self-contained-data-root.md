# Ship portable and installer channels with a self-contained data root

On Windows, AI7 ships a zip portable folder and an NSIS installer, produced from the same source so that neither is a separate product. The portable channel is the reason this Windows design exists: the intended users are publishing professionals on managed corporate machines, and needing no admin rights, no registry writes, and no IT ticket removes a real adoption gate. The predecessor shipped portable builds for the same audience, and dropping the embedded Python interpreter makes the folder substantially smaller. The installer serves users who simply expect one. This revises the original decision, which shipped portable only and deferred an installer until a concrete need appeared. ADR 0028 adds macOS as an equal product platform, and [ADR 0052](./0052-select-the-macos-v1-distribution-and-data-location-profile.md) now owns its deliberately different package/update and data-root mechanics.

In the Windows portable channel the Agent Data Root lives inside the AI7 folder, so that installation is genuinely self-contained: copying the folder moves the work, and backing up the folder backs up everything. Program files and user data are separated within it — `app/` is replaced wholesale on update while `data/` is preserved — and the data root carries a version marker so an older build refuses newer data rather than corrupting it. Where the folder cannot host a writable data root, AI7 detects this on first run, falls back to `%LOCALAPPDATA%\AI7`, and says plainly where the data went rather than failing silently. Under the two-channel revision that fallback stops being an edge case and becomes the installer channel's normal path, since an application installed under Program Files cannot write beside itself; the rule is unchanged, only its frequency. The Protected Secret Store is the deliberate exception in both channels and stays outside in Windows Credential Manager behind the Credential Broker, because a portable folder is designed to be copied and a copied folder carrying credential material to another machine would be a real leak. macOS uses the same Credential Broker contract with a Keychain adapter, while ADR 0052 selects its OS-resolved per-user Application Support data location with no silent fallback.

The residual exposure is that portable folders end up on synced cloud drives, which would carry every manuscript off the machine. This does not violate the egress rule as written, since that rule governs paths AI7 automates while folder placement is a user decision, so the mitigation is detection rather than a different default: AI7 warns clearly, in editorial rather than technical language, when its folder sits beneath a known sync or backup root, and the warning informs without blocking because the user is authorized personnel. Because user data lives inside the application folder in the portable channel, ADR 0016's prohibition extends to the whole folder, which must never sit inside a repository working tree. Applicable complete journeys on Windows cover both channels inside ADR 0027's one logical E2E Functional Gate, without a separate package-verification gate. Windows code signing is deferred until the owner explicitly requests it; unsigned builds trigger SmartScreen, which for a non-expert user on a corporate machine is a hard stop rather than a warning, so this is recorded as a known adoption cost to be paid when chosen rather than as a cosmetic gap. ADR 0052 independently requires a Developer ID-signed, hardened-runtime, notarized DMG for macOS distribution.

## Later refinement

[ADR 0052](./0052-select-the-macos-v1-distribution-and-data-location-profile.md) selects macOS 15+ on Apple Silicon arm64, direct-download DMG/manual application replacement, and the OS-resolved per-user Application Support location for `io.github.zhouy1017.ai7` with no silent fallback. Those rules refine only the previously deferred macOS mechanics; this ADR remains the Windows-channel owner.
