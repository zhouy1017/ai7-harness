# Run an Electron shell with an isolated AI7 service process

Status: **accepted core on Windows and macOS; exact macOS IPC remains proposed under ADR 0027**

AI7 ships as an Electron application over three processes. Electron main is a thin shell owning window lifecycle, file pickers, the single-instance lock, data-root resolution, and the sync-root warning. The renderer holds the AI7 UI and editor with context isolation enabled and Node integration disabled. A separate Node process hosts AI7 domain services and the composed Harness runtime, and that process is the one local AI7 authority. Electron is chosen because AI7 is TypeScript and Node and Harness is Node, so a Node runtime ships regardless. Electron 43.4.0 bundling Node 24.18.1 demonstrates feasibility against the Harness engine requirement, but it is not a durable release pin; scaffold-time selection must choose a then-supported Electron version and recheck Harness and native-module ABI on Windows and macOS. Tauri would add a Rust toolchain while still needing a Node sidecar, since Harness cannot run in Rust — two runtimes to avoid one — and native webview hosting means writing platform glue for a problem Electron already solves.

The service is separate rather than embedded in Electron main for four reasons that each trace to an accepted decision. Parallel Runs are required, so a busy agent loop must never block paint. A provider or Harness failure must not take down an editor holding unsaved text, which the no-silent-loss obligation forbids. The same service must be drivable headlessly, because the pull-request gate and the first tracer slice both need it without a GUI, and a service inside Electron main would force every test through an Electron harness. Finally, the instance-level concurrency and budget governor gets a natural home. Inter-process communication prefers stdio and never opens a TCP listener, which removes the exposed-web-server risk structurally rather than configuring it away. A Windows named pipe remains an accepted option from the earlier decision; a macOS Unix-domain socket is only a candidate, and the exact macOS carrier/protocol adaptation remains open.

The recorded risk that Electron and native dependencies conflict with the Harness package stack is reduced but not closed. The core agent loop is JavaScript and narrowing the dependency graph reduces exposure, yet the exact candidate-package installed closure can still introduce native dependencies. Phase 0 therefore requires installed-closure and ABI evidence from separately authorized disposable audit environments on both supported platforms rather than inferring safety from the core package alone or adding dependencies to the design repository.
