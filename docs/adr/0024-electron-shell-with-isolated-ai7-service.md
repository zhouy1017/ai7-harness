# Run an Electron shell with an isolated AI7 service process

AI7 ships as an Electron application over three processes. Electron main is a thin shell owning window lifecycle, file pickers, the single-instance lock, data-root resolution, and the sync-root warning. The renderer holds the AI7 UI and editor with context isolation enabled and Node integration disabled. A separate Node process hosts AI7 domain services and the composed Harness runtime, and that process is the one local AI7 authority. Electron is chosen because AI7 is TypeScript and Node and Harness is Node, so a Node runtime ships regardless. The implementation plan pins the exact Electron version, its bundled Node version, the Supported Development Host matrix, and one package-manager version after checking the accepted Harness engine range and selected public package metadata together. Tauri would add a Rust toolchain while still needing a Node sidecar, since Harness cannot run in Rust — two runtimes to avoid one — and hosting WebView2 directly means writing native glue for a problem Electron already solves.

The service is separate rather than embedded in Electron main for four reasons that each trace to an accepted decision. Parallel Runs are required, so a busy agent loop must never block paint. A provider or Harness failure must not take down an editor holding unsaved text, which the no-silent-loss obligation forbids. The same service remains directly drivable for focused local diagnosis and process-control hooks, while the product E2E journey and first tracer still launch and traverse renderer, Electron main, service, composed Harness runtime, and domain boundaries; service-only execution never substitutes for that path. Finally, the instance-level concurrency governor, usage observation, and optional explicit Run Budget Ceiling enforcement get a natural home. ADR 0033 later fixes the default ceiling state at `unset` and leaves Provider Account Limits external. Inter-process communication uses stdio or a private platform-local adapter—such as a Windows named pipe when needed—and never a TCP listener, which removes the exposed-web-server risk structurally rather than configuring it away. The macOS carrier is an adapter detail, not a new authority or process.

The recorded risk that Electron and native dependencies could conflict with the Harness package stack is reduced by the narrow package-subset rule, which excludes generic sandbox and shell packages and their native surface. The exact compatibility claim remains an implementation-plan and committed-lockfile fact: the selected Electron-bundled Node, Harness engine range, exact packages, and any native modules are checked together rather than inferred from this ADR.
