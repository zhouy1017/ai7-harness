# Keep development dispatch rules provider-neutral

Repository development uses three agent roles. The Commander decides dispatch, reviews returned work, and is the sole integrator and sole external-action authority. A Worker writes only its own worktree and branch, runs the E2E Functional Gate only when its implementation work affects a supported journey or observed-bug outcome, and reports; it never merges, pushes, publishes, or touches credentials, manuscripts, or private sample Books.

A Reviewer is optional, is never the author, and starts from fresh, strictly read-only context. The Commander directly dispatches every Reviewer, including each parallel review; a Reviewer may not dispatch, delegate to, or spawn another agent. Record the reviewed task class, and bind the Reviewer at that class or higher. Every Reviewer report records requested and actual provider/model/effort, confirmation of the class floor, fresh-context/read-only/non-author independence, fallback status, and any exact fallback or same-provider reason. Cross-provider review is preferred, but Reviewer assignment does not inherit the Worker provider order. Every verdict remains advisory and must not become a pull-request (PR), CI, branch, exact-head, zero-finding, iterative re-review, or other proof gate.

Operating rules are provider-neutral and may never be conditioned on which model is running. Layer B of the dispatch contract is the only provider-specific policy surface: it owns the class-to-model table, Worker provider order and accepted capacity lanes, Reviewer cross-provider preference and binding selection, and quota fallback, while T0 work is never dispatched at all. Effort ladders differ in length and meaning between providers, so bindings map task outcome to setting rather than matching label to label. Codex normally holds the commander seat at top capability because a persistent seat would drain the scarcer provider. The normal order for dispatch-eligible, bounded Worker tasks follows the 2026-08-22 owner revision: select the same-class Claude Code binding first until its usable quota is unavailable or exhausted, then use the same-class Codex fallback. The 2026-08-31 owner revision adds one bounded exception: an existing T1 or T2 coding unit with an exact brief, an identified existing seam, one focused small edit, and deterministic validation may prefer direct `gpt-5.3-codex-spark` @ `xhigh` dispatch when the host exposes available capacity, without a Claude probe. One Spark unavailable or capacity result falls through to the normal same-class order. Spark never binds T0, T3, Commander, or Reviewer work and never changes role authority, validation, one-Worker isolation, reporting, integration, or the task class itself; the detailed exclusions remain in Layer B. Each Worker dispatch records the requested and actual binding plus any exact availability or quota downgrade reason; that operational evidence does not create another policy surface. Ordinary Claude/Codex fallback remains bidirectional and downgrades the provider, never the task class — either provider can be the constrained one, as on 2026-08-17 when Codex was exhausted and Claude was not. Worker selection never transfers Commander, final-integration, external-action, or independent-Reviewer authority, and model or effort capabilities never expand a Reviewer's no-dispatch/no-spawn boundary.

The legacy multi-agent pilot is rejected as a baseline. Its bespoke lifecycle state machine and its host connector with DPAPI and Windows Hello enrollment had not completed required real-host observations at the audit pin and address a host-authority problem this repository does not have. Cross-provider dispatch needs only a thin shim over installed CLIs. Typed authority requests, replay-safe dispatch receipts, and any richer role taxonomy are deferred behind stated triggers. This design governs repository tooling exclusively; it is not AI7 product runtime behavior, its Reviewer is not a product Review Decision, and its Layer B binding policy is not a Provider Resolution Plan.
