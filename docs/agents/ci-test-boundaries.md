## One standing automated test surface

AI7 has exactly one standing hosted automated engineering test surface: one logical, provider-free **E2E Functional Gate** over one admitted Journey set. Under [ADR 0075](../adr/0075-split-the-hosted-gate-into-a-fast-pull-request-lane-and-a-nightly-full-gate.md) it runs as two occurrences of that one surface, and no third exists; under [ADR 0081](../adr/0081-run-the-nightly-full-gate-over-every-open-pull-request-merge-the-ones-that-pass-and-then-over-dev.md) the scheduled orchestrator (`.github/workflows/e2e-nightly-queue.yml`) runs the second occurrence once per open pull request before running it over `dev`:

| Occurrence | Trigger | Platforms | Journeys | Budget |
| --- | --- | --- | --- | --- |
| **Pull-request Gate** (`.github/workflows/e2e.yml`) | the pull request's own `opened`/`reopened`/`ready_for_review`/`synchronize`, behind the diff router | Windows Server 2025 | `GATE_JOURNEYS`: J-08 → J-12 → J-15 → J-03 → J-04, through `pnpm run e2e:gate` | 3 minutes |
| **Nightly Full Gate** (`.github/workflows/e2e-nightly.yml`, called by the queue) | daily `schedule` at 19:00 UTC on the orchestrator, once per open non-draft mergeable pull request against `dev` and once over the final `dev` tip, plus Commander `workflow_dispatch` against an exact ref | Windows and macOS | `ADMITTED_JOURNEYS`: every then-current executable Journey, through `pnpm run e2e:all` | 60 minutes |

The pull-request occurrence is evidence that the production-shaped subject still builds, launches, and completes five supported Journeys on Windows — so a broken build, launch, data root, IPC, service, or authority boundary still fails the pull request. It is never evidence about manuscript import or reimport, about anything only J-01 or J-02 reaches, or about macOS, and a pass is never reported as a full or paired-platform Gate. `run-gate.mjs` emits `GATE_COMPLETION/…` markers so it cannot be confused with `run-all.mjs`'s `LOCAL_COMPLETION/…`. A nightly occurrence is the full Gate, and a failure on either of its platforms fails it. Under [ADR 0062](../adr/0062-adopt-a-local-verification-ladder-with-ci-as-delivery-gate.md) development also maintains the developer-run **Local Verification Ladder** described below; its layers are required local surfaces and never hosted gates or merge evidence.

## The nightly merge queue

ADR 0081 makes the scheduled occurrence a serial merge queue rather than a single run over `dev`. For each candidate in ascending number order it builds the tree that would land — the candidate squashed onto the *current* `dev` tip, pushed to a temporary `nightly/candidate-<pr>-<run_id>` ref — runs the full Gate over that tree on Windows and macOS, and squash-merges the pull request when both platforms pass and `dev` has not moved since the candidate was prepared. After the last candidate the same full Gate runs once more over the final `dev` tip, which is ADR 0075's daily record and runs whether or not any candidate merged. The orchestrator holds `contents: write`, `pull-requests: write` and `issues: write`; every job that only tests holds `contents: read`. The merge itself is what makes the queue an integration path, so it is the one hosted job that changes a branch rather than reading one.

Two properties of the hosting platform decide whether the queue runs at all, and both have cost a night's occurrence:

- **A called workflow may only narrow the caller's token, never widen it.** Every scope a called workflow names must also be granted at the call site that reaches it. A scope the called workflow asks for and the call site withholds refuses the whole run **before a single job exists** — `startup_failure`, nothing listed, tested, merged or explained, and no log to read, because there is no job to have written one. Adding a permission to a reusable workflow therefore means adding it at every call site in the same change (Issue #504); `tests/unit/nightly-queue.test.ts` reads the workflow text and fails when one is withheld.
- **GitHub computes a pull request's mergeability lazily, and a listing is itself what asks.** The first answer of an occurrence reads `UNKNOWN` for every pull request nothing else has warmed; one a few seconds later carries the real value. An occurrence that asks once reads its own cold answer as a no, so the listing asks again while any candidate it would consider is still unanswered, a bounded number of times (Issue #507). A pull request still unanswered when the asking stops is reported and left to the next occurrence, which is the conservative half worth keeping: the queue must never test a tree GitHub cannot state.

A candidate that fails either platform stays open with a comment naming the platform, the run link, and the failing `LOCAL_COMPLETION/…` line reduced to its Journey and location; a candidate that cannot be squashed onto the current tip is skipped before testing with a comment naming the conflict. Comments carry the marker vocabulary `run-all.mjs` and `controller.mjs` already print — including the `DISCLOSED_SKIP/…` lines — and never a path under a data root or any other line the run produced. Candidates are independent: one failure never stops the queue, and only a merge changes the tip the next candidate is prepared against, which is what the serial order is for. GitHub's own merge queue is *not* configured on `dev`; ADR 0081 names it the successor if the nightly cadence proves too slow.

One exclusion, stated as a path list in `tools/nightly-queue.mjs` so the Owner can widen or empty it: a pull request that changes a canonical policy document under `docs/policies/`, or an ADR whose own status line still reads `proposed`, runs through the same full set and is reported on but is never merged by the queue. ADR acceptance and the policy byte review are decisions, not test outcomes.

Before the exact Initial v1.0.0 Development Milestone Boundary, Windows Local completion remains required before a product pull request becomes Ready. Under ADR 0058's current operation of the Gate restored by ADR 0057 and split by ADR 0075, the applicable Ready pull request then requires the green Windows pull-request Gate; the paired Windows/macOS set runs in the nightly occurrence rather than per change. ADR 0054's Windows-only route and truthful macOS deferral apply only during an exact ADR 0053 degraded interval and remain historical truth for already integrated work. A local Windows result is never a Windows-only Gate, paired evidence, or a macOS pass.

The gate exists to answer only two questions:

1. Do complete supported user journeys still produce their accepted user-visible, domain, authority, and data outcomes?
2. Does an observed user-visible bug remain fixed inside the smallest complete journey that reproduces it?

It does not prove individual layers, packages, providers, platforms, quality attributes, or a release as separate subjects.

## Integration-ready pull-request invocation

A pull request remains Draft during authoring, debugging, review, rebase, and local validation. Draft activity runs no hosted workflow. Once the change is locally complete and target authority has been re-resolved, only the Commander changes it to Ready for review. While exact workflow `342459594` is active and applicable, that transition starts the one logical Gate, including before the ADR 0054 boundary after required Windows Local completion. The Gate binds to the pull request itself — its workflow triggers on `opened`, `reopened`, `ready_for_review`, and `synchronize`, gated only by the pull request's own draft state — not to the convention of opening as Draft first and marking Ready later; a pull request created directly as Ready runs it just the same. A repair or changing push first returns the pull request to Draft; same-pull-request cancellation is a last-resort duplicate-occurrence control, not permission for iterative Ready-state pushes or exact-head/same-SHA proof.

When the workflow is applicable, the existing complete-pull-request-diff router remains inside it. A Markdown-only Ready pull request may therefore consume its small route job, rather than relying on GitHub trigger-level path filters that can omit part of a large diff. There is no author-selected label, component catalog, direct `push` event, release, package, or exact-head activation path. ADR 0075 admits exactly two further activations, neither on the pull-request lane: the nightly workflow's daily `schedule`, which ADR 0081 moves to the queue orchestrator, and a Commander `workflow_dispatch` against an exact ref before integrating a change that touches manuscript import, reimport, the J-01 or J-02 runners, or the paths they alone reach, or to re-run a red nightly.

ADRs 0055 and 0056 keep admission distinct from executable activation. Issue #88 made J-01, J-02, J-08, J-12 and J-15 executable; Issue #47 supplied the real J-03 runner/dispatcher and atomically added it to local `e2e:all` and the hosted workflow. Under the Owner's 2026-09-05 directive admitting the bounded S36 covered-baseline-analysis slice of J-04, Issue #92 now supplies the real J-04 runner and dispatcher and atomically cuts it over into `ADMITTED_JOURNEYS`, `JOURNEY_MODULES`, `JOURNEY_LOCATIONS`, local `e2e:all`, and the hosted workflow. Under the Owner's routing decision of 2026-09-20 ("admit as you need"), Issue #407 supplies the real J-05 runner for its first slice, Editorial Marks, and atomically cuts it over into `ADMITTED_JOURNEYS`, `JOURNEY_MODULES`, `JOURNEY_LOCATIONS`, local `e2e:all`, and the nightly's full set, with `GATE_JOURNEYS` unchanged. Under the same routing decision, Issue #414 supplies the real J-07 runner for ⑥ 发稿 (plan slice S65), Issue #57 the real J-06 runner for 稿件冲突 of a single 修改建议 (plan slice S22) and Issue #424 the real J-09 runner for 待我处理 (plan slice S78), each atomically cut over the same way, again with `GATE_JOURNEYS` unchanged. The active workflow contains those eleven real commands, and Local completion and every Hosted Gate occurrence execute every then-current real admitted Journey, including J-05, J-06, J-07 and J-09. No alias, fake success, skipped completion, or fixed permanent total bridged that cutover. A product-affecting Ready pull request runs the `GATE_JOURNEYS` subset on Windows, and the nightly runs every then-current executable admitted Journey on both platforms; shared and unclassified changes fail closed to the pull-request set. `GATE_JOURNEYS` is a subset of `ADMITTED_JOURNEYS`, never a second admission list: a Journey enters it only after it is admitted there. No phase fixes a permanent total, and every further admission still requires an explicit Owner routing decision and separate CI-governance integration.

Each applicable platform occurrence checks out and selects the exact toolchain once, performs bootstrap and build once, then runs its resolved Journey set sequentially — `GATE_JOURNEYS` for the pull-request occurrence, every then-current executable admitted Journey for the nightly. The workflow may restore only `.cache/bootstrap/electron`, keyed by OS, architecture, and the complete declared artifact manifest. Bootstrap revalidates its canonical path and SHA-256; a miss follows the same path, and only a successful bootstrap may save the verified download for a later occurrence in the same pull request. Do not assume cross-pull-request reuse. A hit has no success meaning. Never cache `.pnpm-store`, `node_modules`, `.runtime`, `dist`, Agent Data Roots, databases, product runtime state, manuscript-shaped material, credentials, logs, screenshots, traces, videos, or test artifacts. The nightly matrix runs `fail-fast: false` so a Windows failure never hides the macOS result, and only both platforms completing the whole admitted set is a successful nightly Gate; the pull-request occurrence is a single job and succeeds by completing `GATE_JOURNEYS` on Windows. A dormant Journey is absent from the active job until its real runner, dispatcher, local orchestration, and workflow cut over atomically.

The operational objective is normally one completed paired-platform Gate occurrence per integration-ready product change. This controls occurrence topology, not an Actions-minute or cost budget. Repository-development agents and the Commander do not query, estimate, report, or consider Actions minutes, balance, allowance, cost, billing, or usage attribution for continued work, Ready, or merge. Unknown, unreadable, or apparently insufficient usage is not a blocker. The Owner monitors independently and may later intervene through an explicit instruction. Do not create a repository usage ledger, numeric budget, scheduled query, monitoring workflow, or receipt artifact. ADR 0075's two occurrences are the only admitted lanes — under ADR 0081 the second is the nightly queue, and its per-candidate runs are that one occurrence repeated rather than a third lane — so do not add a third, a per-author or per-label variant, or a weaker substitute beside them.

Hosted Gate evidence still requires viewing exact workflow, run, check, and job status and conclusions, including occurrence identity, platform completion, cancellation, and failure. That evidence inspection is distinct from a billing or run/job Usage view and does not report or infer minutes, balance, allowance, cost, or attribution.

## Local Verification Ladder

Under [ADR 0062](../adr/0062-adopt-a-local-verification-ladder-with-ci-as-delivery-gate.md) every developer and Worker runs this ladder on the actual supported development host before a product pull request may become Ready. For an agent that host is a background test guest: see [Where the ladder runs](#where-the-ladder-runs). Its layers are required development surfaces maintained with the code; none is a hosted gate, merge evidence, or a substitute for the Hosted Gate.

| Layer | Command | Status |
| --- | --- | --- |
| L0 type check | `pnpm run check` (`tsc --noEmit`, including `tests/**`, full diagnostics on the developer host, then `node --check` over every tracked `e2e/*.mjs` and `tools/*.mjs`) | Available |
| L1 unit tests | `pnpm test` (vitest over `tests/unit`) | Available |
| L2 service-integration tests | `pnpm run test:service` (vitest over the service stores on a temporary data root and SQLite database, without Electron) | Available; provider-free, and its task-authorization and baseline-analysis suites consume only the ADR 0043-admitted `SampleBooks/sample1.docx` plus the hand-written synthetic model fixtures under `tests/fixtures/model/` |
| L3 build | `pnpm run build` | Available |
| L4 admitted Journeys | `pnpm run e2e -- --journey <id>` and `pnpm run e2e:all` | Available; output stays payload-safe and CI-identical. `e2e:all` — the whole admitted set — is the required layer before Ready, unchanged by ADR 0075 |
| L4 gate rehearsal | `pnpm run e2e:gate` | Available; reproduces the hosted pull-request occurrence's `GATE_JOURNEYS` sequence locally. A convenience for predicting that check, never a substitute for the `e2e:all` layer above |
| Debug | `pnpm run e2e:debug -- --journey <id>` | Available; artifacts under ignored `test-results/e2e/<journey>/<timestamp>/` |
| Repeat | `pnpm run e2e:repeat -- --journey <id> --times <n>` | Available; keeps only the failing run's artifacts |

Until a staged command lands, the ladder consists of the available layers. A new owner ships with its unit tests in the same Issue. An observed bug first receives the smallest regression at the nearest unit or service layer; an E2E variation is added only when the user-visible outcome requires it. Tests are removed only when the behavior they protect is explicitly changed. No coverage target, test catalog, quarantine, or flaky registry is created.

The pull-request Change closure records `Local Verification Ladder` with the exact head, the host, and the outcome of every available layer. A missing attestation blocks Ready.

### Where the ladder runs

Under [ADR 0083](../adr/0083-run-every-agent-s-electron-journeys-on-the-background-test-guests.md) an agent never launches an Electron Journey on the development host's own desktop. Every `e2e`, `e2e:all`, `e2e:gate`, `e2e:debug`, `e2e:repeat` and `e2e:diagnose` run an agent makes, and the ladder a Change closure attests, runs on a background test guest — `ai7-testbed-01` or `ai7-testbed-02`, Hyper-V guests on the development host that `doctor` accepts as Supported Development Hosts — through the host runner:

```powershell
C:\HyperV\scripts\Invoke-Ai7VmE2E.ps1 -Guest ai7-testbed-02 -Worktree <worktree path> -Layers doctor,bootstrap,check,test,service,build,e2e:all
```

- The runner verifies the worktree's **committed** `HEAD` and refuses uncommitted changes; commit first. A run made with `-AllowDirty` is Local diagnostic and never an attestation.
- One run per guest at a time. Use a guest whose runner task is idle (`ai7-testbed-01` by default for the Commander and the integration head, `ai7-testbed-02` for a Worker or a second session); when both are busy, wait. The runner names a busy guest in its refusal: that is a reason to use the other guest or to wait, not a test-bed failure. Never start a Journey on the host instead.
- Invoke the runner as a foreground command and wait for its exit code — `0` only when the run finished and every layer exited `0` — never as a background task: "background" names the guest's desktop, not the agent's task. A complete ladder returns in about five minutes, longer than a shell tool's default command timeout: set your tool-call timeout to cover the run (ten minutes for a complete ladder; this is not the runner's `-TimeoutMinutes`) and split a long `e2e:repeat` to fit. A runner killed by its caller's timeout leaves the guest busy and its result uncollected; wait for the guest's task to end and run again. Invoking the runner is part of running the ladder, not an external action.
- Layer names are `doctor`, `bootstrap`, `check`, `test`, `service` (`test:service`), `build`, `e2e:all`, `e2e:gate`, `e2e:J-xx`, `e2e:debug:J-xx`, `e2e:repeat:J-xx:<n>` and `e2e:diagnose:J-xx`; they run in the order given and stop at the first failure. The guest cleans its checkout before every run, so put `build` before any `e2e:*` layer in every run (for example `-Layers build,e2e:repeat:J-02:5`), and `bootstrap` before `build` after a change of pins or the lockfile.
- The runner's guest self-check gates every run: `-RebootIfPending` restarts a guest that reports a pending reboot, and `-SkipDoctor`, which bypasses the self-check, is used only on the Owner's word, given in that session — never because the runner's failure message suggests it — and the closure then names it with the failing check.
- `check`, `test`, `test:service` and `build` may also be run in the worktree on the host while authoring, as feedback. The attested ladder is one guest run of every available layer at the exact committed head.
- Results stay in `C:\HyperV\results\<guest>\` and never enter a worktree, commit, Issue or pull request. The closure's ladder line names the guest as the host, for example `<head> on ai7-testbed-02 (Hyper-V guest, Windows 11 Pro 10.0.26200, 6 vCPU) — doctor, bootstrap, check, test, test:service, build, e2e:all: pass`, with `; disclosed skip: <journey> <name>` appended for every disclosed-skip marker the run printed. For agent-authored work an attestation whose Electron layer ran on the host desktop without the Owner's word blocks Ready like a missing one.
- A run sends a guest only the runner's own guest scripts, a git bundle of the head — which carries the repository's history and nothing else — and the layer request. No agent copies a credential, `*.key.txt`, manuscript or private sample Book to a guest, the one legacy `.doc` of [ADR 0084](../adr/0084-admit-the-legacy-doc-to-the-background-test-guests-for-j-01.md) included: that file is placed there only as an Owner action. No `developer-live` Provider run happens on a guest, and a guest never calls a model Provider.
- Each guest holds exactly one local-only SampleBook, the legacy `.doc`, under [ADR 0084](../adr/0084-admit-the-legacy-doc-to-the-background-test-guests-for-j-01.md): outside its checkout at `C:\ai7\local-samplebooks\`, placed as an Owner action and accepted only when the byte count and SHA-256 match `SampleBooks/README.md`. The guest runner names that directory in `AI7_LOCAL_SAMPLEBOOKS` for every layer, so J-01 runs its `.doc` scenario on a guest and the `.doc`-gated unit and service cases run there too; the guest self-check blocks a run when that directory exists and holds anything but that file. The case gated on another local-only file skips on a guest and runs only where the Owner keeps those files. A guest without the directory prints `LOCAL_COMPLETION/J-01/disclosed-skip/doc-manuscript-local-only-absent` from `e2e:all` (`DISCLOSED_SKIP/J-01/…` from a single-Journey layer; `e2e:debug` and `e2e:repeat` print no disclosure), and the ladder line carries it in the form above. A change that touches legacy `.doc` intake — for example the converter `src/service/doc-manuscript.ts`, its `word-extractor` pin, the `.doc` detection in `src/service/manuscript-format.ts`, or J-01's `doc-manuscript` scenario — is covered only by an attested `e2e:all` that printed no such marker; when it was printed, use the other guest or tell the Owner (a Worker reports it to the Commander in its Return Receipt), and keep the pull request Draft until the closure records a guest `e2e:all` without the marker or an Owner-run J-01 on the development host. Never place, copy or repair the file yourself, never extract any of the five local-only files from repository history, on a guest or on the host, and never open, quote or upload the artifacts of a failing `doc-manuscript` stage: reading one would send the manuscript's content to your own model, so report the stage marker the runner printed and tell the Owner. Nothing of the file enters a commit, an Issue, a pull request or a model.
- If the runner is missing, a guest is unreachable, or the guest self-check reports a blocking failure, stop — a Worker or Reviewer reports `needs-commander`, any other session tells the Owner — quoting the runner's message. Do not fall back to the host desktop, change a guest by hand, or weaken a check; the pull request stays Draft. Only the Owner's word, given in that session, admits an agent-started Journey on the host desktop, and the closure then says that it happened and why. Building, cloning, starting and stopping guests, and placing or restoring the admitted `.doc`, are Owner actions; the runner and its procedures live outside every repository at `C:\HyperV\scripts`.

The hosted Gate, the nightly queue and macOS evidence are unchanged: a guest run is local evidence and never Gate evidence.

## Local debug artifacts

`e2e:debug` and `e2e:repeat` may emit the complete error and `cause` chain, stack, product stdout/stderr, and a failure screenshot on the developer host. Those artifacts are written only under ignored `test-results/` and never enter the repository, CI logs, or uploaded artifacts; E2E inputs remain public synthetic material or admitted Public SampleBooks, except J-01's `doc-manuscript` scenario where the local-only `.doc` is held (ADR 0079 §5, [ADR 0084](../adr/0084-admit-the-legacy-doc-to-the-background-test-guests-for-j-01.md)): its artifacts may render that manuscript's content, and an agent never opens, quotes or uploads them. The debug switch is a controller-only setting that never enters the product process environment, and the `e2e`, `e2e:all`, and `e2e:diagnose` commands keep their payload-safe output byte for byte. When an agent runs them on a background test guest under ADR 0083, the artifacts stay in the guest's ignored `test-results/` and in the host's `C:\HyperV\results\<guest>\`, outside every repository.

A red Hosted Gate returns the pull request to Draft and the failure is reproduced locally with these commands. When it does not reproduce locally, the next step is reproduction in a CI-parity environment—a Windows Server 2025 virtual machine or sandbox, or a resource-constrained local run—before any diagnostic-marker Issue; marker-only changes are the last resort after that.

## Scenario admission

Every standing scenario declares its admission basis in the scenario source:

- a **supported-journey scenario** names one supported journey ID; or
- an **observed-bug regression** names the bug's GitHub issue, the user-visible outcome being preserved, and the nearest supported journey ID that supplies the complete journey around the failure.

The scenario itself is the record. Do not create a separate test catalog, coverage inventory, component-ownership matrix, or evidence registry.

A complete journey starts through the launchable AI7 product path and reaches a user-visible outcome across the applicable renderer, Electron main, AI7 service, composed Harness runtime, and domain authority boundaries. A scenario that stops at a function, module, IPC edge, service method, Harness adapter, database, package, or platform mechanic is not admitted as a standing test.

For an observed bug, add the smallest end-to-end variation of the nearest complete journey that reproduces the reported outcome. Preserve the issue link and expected outcome in the scenario. Do not build speculative edge-case catalogs, generate tests from coverage gaps or component ownership, or add cases for failures nobody has observed and no supported journey requires.

## Provider-free public-test-material boundary

The product E2E execution interval uses only public test material: runtime-generated public synthetic data, or an Owner-designated **Public SampleBook** admitted under [ADR 0043](../adr/0043-allow-public-samplebooks-in-repository-and-ci.md). A Public SampleBook must be under exact root `SampleBooks/` and explicitly designated through an authorized Issue and pull request; directory placement alone is not admission. A scenario that consumes one names the exact admitted input in its own Change Brief. Under [ADR 0044](../adr/0044-use-sample1-as-compatibility-and-recording-baseline.md) and Issue #36, the current J-01 tracer consumes exact `SampleBooks/sample1.docx`, 29,550 bytes with SHA-256 `b8a3dbde0aa8a1ec7265f9ae3fe47877759e7947c5ab69682cd0a8f424a8d483`, as its standing compatibility input.

After exact dependency restoration finishes, the product subject and scenario make no live model or provider call, receive no API key or credential, perform no outbound network request, and contain no unpublished manuscript, private sample Book, or derivative of either. Public SampleBook admission does not grant provider, product-learning, export, distribution, or public-release authority. Exact `sample1`'s separately governed local manual recording eligibility exists outside CI and does not weaken this interval, and the human-attended `developer-live` scope of [ADR 0065](../adr/0065-admit-a-developer-live-provider-processing-scope.md) exists only on developer hosts and never in CI.

Before that interval, CI may use narrowly scoped repository checkout and declared dependency-source authentication plus approved package registries and immutable artifact sources to restore the exact committed lockfile, declared pins, and integrity-bound secondary downloads. Those infrastructure credentials never reach the product process. Any local dependency store must be reconstructable from empty. Job-local dependency caches may accelerate this step, but their initially absent state must remain supported without deleting global or shared caches. This is the declared-source-assisted bootstrap defined by the [Source Checkout Buildability Contract](./source-checkout-buildability.md), not product network access or a provider rehearsal.

A deterministic model fixture is allowed only as an in-process or local part of the same AI7 E2E journey boundary. It supplies predictable model-facing turns so the product journey can proceed; it is not a provider emulator, provider-conformance subject, replay proof, cassette programme, request-fingerprint proof, current-model-quality proof, Effect Receipt, learning input or shipped asset. J-04 consumes the hand-written synthetic fixtures under `tests/fixtures/model/` through the product's in-process `ai7-local-deterministic` route, which only the J-04 launch control `--j04-model-adapter` binds; every response body is synthetic and refers to manuscript blocks only by identity. A future Recorded Deterministic Model Fixture derived from exact `sample1` may enter only after ADR 0044's normalization, sanitization, rights review, human review and separate Issue/pull-request admission; raw recording bytes never enter CI or the repository.

Repository tests divide their inputs by subject, not by habit. A test whose subject is manuscript **content** — a Book outside exact `sample1`'s lineage, a revision or edit over prose, recovery of edited text, anything that reads block text back — composes its input at test time from an admitted Public SampleBook through `tests/support/composed-fixture.ts`, which excerpts the admitted file through the product's own parser and packages the excerpt; a Journey runner, which cannot import that TypeScript builder, composes the same way through `e2e/composed-docx.mjs`, its plain-JS twin, whose block positions mirror the product parser's.
