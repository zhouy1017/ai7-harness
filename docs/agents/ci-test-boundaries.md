## One standing automated test surface

AI7 has exactly one standing hosted automated engineering test surface: one logical, provider-free **E2E Functional Gate** over one admitted Journey set. Under [ADR 0075](../adr/0075-split-the-hosted-gate-into-a-fast-pull-request-lane-and-a-nightly-full-gate.md) it runs as two occurrences of that one surface, and no third exists; under [ADR 0081](../adr/0081-run-the-nightly-full-gate-over-every-open-pull-request-merge-the-ones-that-pass-and-then-over-dev.md) the scheduled orchestrator (`.github/workflows/e2e-nightly-queue.yml`) runs the second occurrence once per open pull request before running it over `dev`:

| Occurrence | Trigger | Platforms | Journeys | Budget |
| --- | --- | --- | --- | --- |
| **Pull-request Gate** (`.github/workflows/e2e.yml`) | the pull request's own `opened`/`reopened`/`ready_for_review`/`synchronize`/`edited`, against its wave or `dev`, behind the complete-diff router | Windows Server 2025 | `GATE_JOURNEYS`: J-08 → J-12 → J-15 → J-03 → J-04, through `pnpm run e2e:gate` | 3 minutes |
| **Nightly Full Gate** (`.github/workflows/e2e-nightly.yml`, called by the queue) | daily `schedule` at 19:00 UTC on the orchestrator, once per open non-draft mergeable slice/final candidate and once over the final `dev` tip, plus the responsible integration role’s `workflow_dispatch` against an immutable commit | Windows Server 2025 only — the macOS entry is deferred indefinitely under [ADR 0097](../adr/0097-defer-the-macos-platform-indefinitely-and-deliver-windows-only.md) | `ADMITTED_JOURNEYS`: every then-current executable Journey, through `pnpm run e2e:all` | 60 minutes |

Resolve the executable sequence at the candidate head from `ADMITTED_JOURNEYS` and its `GATE_JOURNEYS` subset in [the E2E controller](../../e2e/controller.mjs); [E2E journeys](../development/e2e-journeys.md) owns the supported scenarios and evidence. Neither a historical cutover list nor a copied command count replaces that admission owner.

The pull-request occurrence is evidence that the production-shaped subject still builds, launches, and completes five supported Journeys on Windows — so a broken build, launch, data root, IPC, service, or authority boundary still fails the pull request. It is never evidence about manuscript import or reimport or about anything only J-01 or J-02 reaches, and a pass is never reported as a full Gate. `run-gate.mjs` emits `GATE_COMPLETION/…` markers so it cannot be confused with `run-all.mjs`'s `LOCAL_COMPLETION/…`. A nightly occurrence is the full Gate: its one Windows job completing the whole admitted set. It has no macOS job while [ADR 0097](../adr/0097-defer-the-macos-platform-indefinitely-and-deliver-windows-only.md) holds, so there is no macOS evidence to miss. Under [ADR 0062](../adr/0062-adopt-a-local-verification-ladder-with-ci-as-delivery-gate.md) development also maintains the developer-run **Local Verification Ladder** described below; its layers are available local surfaces selected for the outcome and never additional hosted gates or substitutes for hosted Gate evidence.

## Existing nightly queue and exact-candidate tests

The ADR 0081 queue lists open non-draft mergeable development PRs, in ascending PR order with `max-parallel: 1`; branch naming is a convention, and `main` remains excluded. Each candidate is squashed onto its actual current target tip and pushed to the existing temporary `nightly/candidate-<pr>-<run_id>` ref. The Windows job must pass that exact tree; the current head, target/base and complete diff are reread before merge. Changed head/base refuses a stale merge even when earlier checks are green. After the last candidate the same full Gate runs once over the final `dev` tip. Only final dev integration closes linked Issues; slice integration does not claim dev completion. Session dispatch determines the merge owner; a Worker does not merge its own slice when the Commander owns integration.

The queue runs only from trusted `dev`. Privileged listing/preparation/merge/cleanup execute dev control code, never code selected by a candidate. The Windows test job explicitly holds only `contents: read` and disables checkout credential persistence. The merge job additionally needs `actions: read` to inspect the actual test job; every reusable call site grants the scopes its callee needs. This remains the existing Gate, not another hosted proof lane.

The Owner-authorized manual full-Gate path also supports refreshing reviewed CI control before it reaches `dev` (#1279/#1280/#1290). Explicitly dispatch the existing `e2e-nightly.yml` from the reviewed control revision, supplying `ref` as the exact current PR head, `pr` as its number and `base` as its exact current base. The resolver admits only an open, non-draft, same-repository PR targeting a branch other than main, with the current base already in its head ancestry. Source-branch names remain unrestricted. Resolve/publish jobs check out the dispatch's immutable `github.workflow_sha`, not candidate code; GitHub documents this [workflow-source identity](https://docs.github.com/en/actions/reference/workflows-and-actions/contexts#github-context). The existing Windows full-Journey job alone executes the candidate with a read-only token. Reading a control or PR source revision from `main` is not main promotion; target promotion authority remains separate.

After actual full-job success, the trusted publisher reads that same run/attempt's job identities and conclusions from the Actions API and rechecks the PR plus fetched head/base before and after publishing the **existing** `E2E Functional Gate` context. Failed, cancelled, skipped, wrong-run/control/job or moved-candidate evidence cannot produce success. This adds no hosted test Gate, receipt, coding-model/branch whitelist or protection bypass. The Commander reviews the concrete control diff and owns the final dispatch/merge; the workflow's selected control SHA and tested PR head/base remain distinct evidence. Ref-only manual runs and queue calls retain their existing full-test behavior without publishing a PR status. Reusable callers grant the optional publisher's declared scopes even when it is skipped; the test job still narrows itself to `contents: read`.

Two properties of the hosting platform decide whether the queue runs at all, and both have cost a night's occurrence:

- **A called workflow may only narrow the caller's token, never widen it.** Every scope a called workflow names must also be granted at the call site that reaches it. A scope the called workflow asks for and the call site withholds refuses the whole run **before a single job exists** — `startup_failure`, nothing listed, tested, merged or explained, and no log to read, because there is no job to have written one. Adding a permission to a reusable workflow therefore means adding it at every call site in the same change (Issue #504); `tests/unit/nightly-queue.test.ts` reads the workflow text and fails when one is withheld.
- **GitHub computes a pull request's mergeability lazily, and a listing is itself what asks.** The first answer of an occurrence reads `UNKNOWN` for every pull request nothing else has warmed; one a few seconds later carries the real value. An occurrence that asks once reads its own cold answer as a no, so the listing asks again while any candidate it would consider is still unanswered, a bounded number of times (Issue #507). A pull request still unanswered when the asking stops is reported and left to the next occurrence, which is the conservative half worth keeping: the queue must never test a tree GitHub cannot state.

A candidate whose Windows job fails stays open with a comment naming the platform, the run link, and the failing `LOCAL_COMPLETION/…` line reduced to its Journey and location; a candidate that cannot be squashed onto the current tip is skipped before testing with a comment naming the conflict. Comments carry the marker vocabulary `run-all.mjs` and `controller.mjs` already print — including the `DISCLOSED_SKIP/…` lines — and never a path under a data root or any other line the run produced. Candidates are independent: one failure never stops the queue, and only a merge changes the tip the next candidate is prepared against, which is what the serial order is for. GitHub's own merge queue is *not* configured on `dev`; ADR 0081 names it the successor if the nightly cadence proves too slow.

One exclusion, stated as a path list in `tools/nightly-queue.mjs` so the Owner can widen or empty it: a pull request that changes a canonical policy document under `docs/policies/`, or an ADR whose own status line still reads `proposed`, runs through the same full set and is reported on but is never merged by the queue. ADR acceptance and the policy byte review are decisions, not test outcomes.

The gate exists to answer only two questions:

1. Do complete supported user journeys still produce their accepted user-visible, domain, authority, and data outcomes?
2. Does an observed user-visible bug remain fixed inside the smallest complete journey that reproduces it?

It does not prove individual layers, packages, providers, platforms, quality attributes, or a release as separate subjects.

### Trusted Gate projection and merge controls

The existing PR workflow uses `pull_request_target` for trusted control execution. Route/result jobs check out dev; the Journey job checks out the exact same-repository candidate head with only `contents: read` and no persisted credentials. Fork code does not run with the repository's cache scope. Only the trusted result job has `statuses: write`; it projects the actual Route/build/Journey result onto the exact head/base as `E2E Functional Gate`. Build/test failure, cancellation or a moved candidate fails the status; a complete Markdown-only diff may skip Journeys. There is no comment-triggered authorization refresh, model or branch-name allowlist, or Orca receipt prerequisite. A title/body edit neither reruns nor cancels Journeys; a base change is a new candidate.

The Commander configures strict required `E2E Functional Gate` status from the GitHub Actions app (`app_id: 15368`) on dev and assigned integration targets, preserving other protections and enforcing them for administrators. Native GitHub auto-merge remains disabled: the existing serial queue or assigned role's guarded helper owns merging. Workflow edits do not configure repository protection.

From trusted dev control code, `node tools/nightly-queue.mjs prepare --pr <n>` builds the existing exact candidate and reports `head`, target branch in `dev`, target tip in `devTip`, `commit` and temporary `ref`. The guarded merge command is `node tools/nightly-queue.mjs merge --pr <n> --head <head> --expected-dev-tip <base> --candidate <prepared-commit> --gate-run <run-id>` (`--dry-run` rehearses without merging), followed by `cleanup --ref <ref>`. It verifies the actual successful fast PR Gate or full Gate jobs at the current candidate/tree, without role comments. The queue verifies its current occurrence, temporary ref and prepared tree; Owner-reserved policy/proposed-ADR candidates remain excluded from automatic merging. GitHub's merge API checks head atomically, so the helper rereads head/base immediately before the serial merge; it is not target compare-and-swap against an external simultaneous merge. Main promotion remains separate.

Under [ADR 0093](../adr/0093-automate-nightly-packages-and-windows-version-tag-releases.md), the queue passes the immutable final dev SHA to the Windows full Gate and subsequent packaging. Packaging starts only after that Gate passes; version-tag publication consumes those outputs and adds no Gate.

## Integration-ready pull-request invocation

Use Draft when helpful during unfinished work; session instructions and applicable verification determine readiness. Run checks proportionate to the change, fix actual failures, and state the tested candidate and skips in the PR. No role evidence or full-ladder attestation is required merely to open a Ready PR. Same-pull-request cancellation remains a duplicate-occurrence control.

When the workflow is applicable, the existing complete-pull-request-diff router remains inside it. A Markdown-only Ready pull request may therefore consume its small route job, rather than relying on GitHub trigger-level path filters that can omit part of a large diff. There is no author-selected label, component catalog, direct `push` event, release, package, or exact-head activation path. ADR 0075 admits exactly two further activations, neither on the pull-request lane: the nightly workflow's daily `schedule`, which ADR 0081 moves to the queue orchestrator, and the responsible integration role’s `workflow_dispatch` against an exact ref before integrating a change that touches manuscript import, reimport, the J-01 or J-02 runners, or the paths they alone reach, or to re-run a red nightly.

ADRs 0055 and 0056 keep admission distinct from executable activation. Those cutovers established the executable admitted set. Local completion and the Nightly Full Gate execute every then-current admitted Journey; the pull-request Gate executes only `GATE_JOURNEYS`. No alias, fake success, skipped completion, or fixed permanent total bridged that cutover. A product-affecting Ready pull request runs the `GATE_JOURNEYS` subset on Windows, and the nightly runs every then-current executable admitted Journey on Windows; shared and unclassified changes fail closed to the pull-request set. `GATE_JOURNEYS` is a subset of `ADMITTED_JOURNEYS`, never a second admission list: a Journey enters it only after it is admitted there. No phase fixes a permanent total, and every further admission still requires an explicit Owner routing decision and separate CI-governance integration.

Each applicable platform occurrence checks out and selects the exact toolchain once, performs bootstrap and build once, then runs its resolved Journey set sequentially — `GATE_JOURNEYS` for the pull-request occurrence, every then-current executable admitted Journey for the nightly. The workflow may restore only `.cache/bootstrap/electron`, keyed by OS, architecture, and the complete declared artifact manifest. Bootstrap revalidates its canonical path and SHA-256; a miss follows the same path, and only a successful bootstrap may save the verified download for a later occurrence in the same pull request. Do not assume cross-pull-request reuse. A hit has no success meaning. Never cache `.pnpm-store`, `node_modules`, `.runtime`, `dist`, Agent Data Roots, databases, product runtime state, manuscript-shaped material, credentials, logs, screenshots, traces, videos, or test artifacts. The nightly matrix holds a single Windows Server 2025 entry under [ADR 0097](../adr/0097-defer-the-macos-platform-indefinitely-and-deliver-windows-only.md), and only that job completing the whole admitted set is a successful nightly Gate; the pull-request occurrence is a single job and succeeds by completing `GATE_JOURNEYS` on Windows. A dormant Journey is absent from the active job until its real runner, dispatcher, local orchestration, and workflow cut over atomically.

The operational objective is normally one completed Gate occurrence per integration-ready product change. This controls occurrence topology, not an Actions-minute or cost budget. Repository-development agents and the Commander do not query, estimate, report, or consider Actions minutes, balance, allowance, cost, billing, or usage attribution for continued work, Ready, or merge. Unknown, unreadable, or apparently insufficient usage is not a blocker. The Owner monitors independently and may later intervene through an explicit instruction. Do not create a repository usage ledger, numeric budget, scheduled query, monitoring workflow, or receipt artifact. ADR 0075's two occurrences are the only admitted lanes — under ADR 0081 the second is the nightly queue, and its per-candidate runs are that one occurrence repeated rather than a third lane — so do not add a third, a per-author or per-label variant, or a weaker substitute beside them.

Hosted Gate evidence still requires viewing exact workflow, run, check, and job status and conclusions, including occurrence identity, platform completion, cancellation, and failure. That evidence inspection is distinct from a billing or run/job Usage view and does not report or infer minutes, balance, allowance, cost, or attribution.

## Local Verification Ladder

The Local Verification Ladder is a menu of maintained development checks. Select the applicable layers under the current Issue/session instructions; full cumulative validation can still be requested for final integration. Electron Journeys run on the background test guest through the host runner below. Local results never substitute for hosted Gate evidence.

| Layer | Command | Status |
| --- | --- | --- |
| L0 type check | `pnpm run check` (`tsc --noEmit`, including `tests/**`, full diagnostics on the developer host, then `node --check` over every tracked `e2e/*.mjs` and `tools/*.mjs`) | Available |
| L1 unit tests | `pnpm test` (vitest over `tests/unit`) | Available |
| L2 service-integration tests | `pnpm run test:service` (vitest over the service stores on a temporary data root and SQLite database, without Electron) | Available; provider-free, and its task-authorization and baseline-analysis suites consume only the ADR 0043-admitted `SampleBooks/sample1.docx` plus the hand-written synthetic model fixtures under `tests/fixtures/model/` |
| L3 build | `pnpm run build` | Available |
| L4 admitted Journeys | `pnpm run e2e -- --journey <id>` and `pnpm run e2e:all` | Available; output stays payload-safe and CI-identical. `e2e:all` runs the whole admitted set when full validation is requested |
| L4 gate rehearsal | `pnpm run e2e:gate` | Available; reproduces the hosted pull-request occurrence's `GATE_JOURNEYS` sequence locally. Rehearses the existing bounded Gate; report it as subset validation |
| Debug | `pnpm run e2e:debug -- --journey <id>` | Available; artifacts under ignored `test-results/e2e/<journey>/<timestamp>/` |
| Repeat | `pnpm run e2e:repeat -- --journey <id> --times <n>` | Available; keeps only the failing run's artifacts |

Until a staged command lands, the ladder consists of the available layers. A new owner ships with its unit tests in the same Issue. An observed bug first receives the smallest regression at the nearest unit or service layer; an E2E variation is added only when the user-visible outcome requires it. Tests are removed only when the behavior they protect is explicitly changed. No coverage target, test catalog, quarantine, or flaky registry is created.

The PR records exact head/base, host, commands, outcomes and disclosed skips for the checks actually run; it does not claim unused layers.

### Where the ladder runs

Under [ADR 0083](../adr/0083-run-every-agent-s-electron-journeys-on-the-background-test-guests.md) an agent never launches an Electron Journey on the development host's own desktop. Every `e2e`, `e2e:all`, `e2e:gate`, `e2e:debug`, `e2e:repeat` and `e2e:diagnose` run an agent makes, and any full guest ladder explicitly requested by the session, runs on a background test guest — one of the pool `ai7-testbed-01`, `ai7-testbed-02` and `ai7-testbed-03` (listed in the runner's `C:\HyperV\scripts\guests.txt`), Hyper-V guests on the development host that `doctor` accepts as Supported Development Hosts — through the host runner:

```powershell
C:\HyperV\scripts\Invoke-Ai7VmE2E.ps1 -Guest ai7-testbed-02 -Worktree <worktree path> -Layers doctor,bootstrap,check,test,service,build,e2e:all
```

- The runner verifies the worktree's **committed** `HEAD` and refuses uncommitted changes; commit first. A run made with `-AllowDirty` is Local diagnostic and never an attestation.
- One run per guest at a time, and the runner queues ([#1463](https://github.com/zhouy1017/ai7-harness/issues/1463)). `-Guest auto` takes the first free guest of the pool; a named guest (`-Guest ai7-testbed-02-nat`) is still accepted. When every candidate is busy the runner waits its turn, first come first served, for up to `-WaitMinutes` (default 180) and prints who holds the guest; `-NoWait` restores the immediate refusal. Do not pre-check or retry around the runner. `C:\HyperV\queue\<machine>.holder.json` names the current holder. Never start a Journey on the host instead.
- Invoke the runner as a foreground command and wait for its exit code — `0` only when the run finished and every layer exited `0` — never as a background task: "background" names the guest's desktop, not the agent's task. A complete single-guest ladder takes about forty minutes and a queued request also waits its turn, both longer than a shell tool's command timeout (this is not the runner's `-TimeoutMinutes`, which bounds the run from its start): when the tool moves the runner to the background, collect that same process's exit and never start it a second time. A runner killed by its caller leaves the guest busy and its result uncollected; the queue lets the next request in when the guest's task ends. Invoking the runner is part of running the ladder, not an external action.
- Layer names are `doctor`, `bootstrap`, `check`, `test`, `service` (`test:service`), `service:<i>/<n>` (shard `i` of `n` of the service tests; the shards of one `n` are disjoint and together cover every file), `build`, `e2e:all`, `e2e:gate`, `e2e:J-xx`, `e2e:debug:J-xx`, `e2e:repeat:J-xx:<n>` and `e2e:diagnose:J-xx`; they run in the order given and stop at the first failure, unless `-ContinueOnFailure` asks for every layer to run and every exit to be recorded. The guest cleans its checkout before every run, so put `build` before any `e2e:*` layer in every run (for example `-Layers build,e2e:repeat:J-02:5`), and `bootstrap` before `build` after a change of pins or the lockfile.
- The runner's guest self-check gates every run: `-RebootIfPending` restarts a guest that reports a pending reboot, and `-SkipDoctor`, which bypasses the self-check, is used only on the Owner's word, given in that session — never because the runner's failure message suggests it — and the closure then names it with the failing check.
- **A slice runs the part of the ladder its change touches; the full ladder runs at each merged integration tip.** A slice's final guest run is `doctor,bootstrap,check,test,build` plus the Journeys its change reaches — the pull-request Gate set (`e2e:gate`) and every Journey that consumes a changed runner file or helper — and `service` only when the change touches `src/service`, `src/shared` or a module that a file under `tests/service` imports. A change that reaches most Journeys (a shared E2E helper) still runs `e2e:all`. Repairs use the short `e2e:debug:J-xx` and `e2e:J-xx` runs. The Commander runs the full ladder at every merged integration tip with `C:\HyperV\scripts\Invoke-Ai7VmLadder.ps1 -Worktree <tip worktree> -ContinueOnFailure`, which splits `check`, `test`, the service shards, `build` and every admitted Journey over the free guests, runs the parts concurrently and writes one combined receipt `C:\HyperV\results\ladders\<stamp>-<sha>.json`; its `coverage` entry is the evidence that each layer and Journey ran once. A failure at the tip goes back to the slice that caused it.
- `check`, `test`, `test:service` and `build` may also be run in the worktree on the host while authoring, as feedback. Record those host results truthfully; when a full guest ladder is requested, run the selected layers at the exact committed head.
- Results stay in `C:\HyperV\results\<guest>\` and never enter a worktree, commit, Issue or pull request. The closure's ladder line names the guest as the host, for example `<head> on ai7-testbed-02 (Hyper-V guest, Windows 11 Pro 10.0.26200, 6 vCPU) — doctor, bootstrap, check, test, test:service, build, e2e:all: pass`, with `; disclosed skip: <journey> <name>` appended for every disclosed-skip marker the run printed. A split ladder names every guest it used and the combined receipt's wall-clock time in the same line. For agent-authored work an attestation whose Electron layer ran on the host desktop without the Owner's word blocks Ready like a missing one.
- A run sends a guest only the runner's own guest scripts, a git bundle of the head — which carries the repository's history and nothing else — and the layer request. No agent copies a credential, `*.key.txt`, manuscript or private sample Book to a guest, the one legacy `.doc` of [ADR 0084](../adr/0084-admit-the-legacy-doc-to-the-background-test-guests-for-j-01.md) included: that file is placed there only as an Owner action. Ordinary automated guest Journeys remain provider-free and never carry product credentials. The separately Owner-authorized #1290 packaged ordinary-production acceptance may use the local guest and task-owned production credential references: only the enrollment helper sends values through authenticated encrypted SSH stdin and a nonce-scoped, in-memory named pipe into the guest interactive session’s protected store, with no secret in argv, generic environments, files, bundles, request/result JSON, logs, artifacts or packages. The helper clears those references after that separate phase. This exception grants no live access to CI or ordinary Journeys.
- Each guest holds exactly one local-only SampleBook, the legacy `.doc`, under [ADR 0084](../adr/0084-admit-the-legacy-doc-to-the-background-test-guests-for-j-01.md): outside its checkout at `C:\ai7\local-samplebooks\`, placed as an Owner action and accepted only when the byte count and SHA-256 match `SampleBooks/README.md`. The guest runner names that directory in `AI7_LOCAL_SAMPLEBOOKS` for every layer, so J-01 runs its `.doc` scenario on a guest and the `.doc`-gated unit and service cases run there too; the guest self-check blocks a run when that directory exists and holds anything but that file. The case gated on another local-only file skips on a guest and runs only where the Owner keeps those files. A guest without the directory prints `LOCAL_COMPLETION/J-01/disclosed-skip/doc-manuscript-local-only-absent` from `e2e:all` (`DISCLOSED_SKIP/J-01/…` from a single-Journey layer; `e2e:debug` and `e2e:repeat` print no disclosure), and the ladder line carries it in the form above. A change that touches legacy `.doc` intake — for example the converter `src/service/doc-manuscript.ts`, its `word-extractor` pin, the `.doc` detection in `src/service/manuscript-format.ts`, or J-01's `doc-manuscript` scenario — is covered only by an attested `e2e:all` that printed no such marker; when it was printed, use the other guest or tell the Owner (the assigned agent reports it in the Issue/PR and Orca task record), and keep the pull request Draft until the closure records a guest `e2e:all` without the marker or an Owner-run J-01 on the development host. Never place, copy or repair the file yourself, never extract any of the five local-only files from repository history, on a guest or on the host, and never open, quote or upload the artifacts of a failing `doc-manuscript` stage: reading one would send the manuscript's content to your own model, so report the stage marker the runner printed and tell the Owner. Nothing of the file enters a commit, an Issue, a pull request or a model.
- If the runner is missing, a guest is unreachable, or the guest self-check reports a blocking failure, stop — a Worker or Reviewer reports `needs-commander`, any other session tells the Owner — quoting the runner's message. Do not fall back to the host desktop, change a guest by hand, or weaken a check; the pull request stays Draft. Only the Owner's word, given in that session, admits an agent-started Journey on the host desktop, and the closure then says that it happened and why. Building, cloning, starting and stopping guests, and placing or restoring the admitted `.doc`, are Owner actions; the runner and its procedures live outside every repository at `C:\HyperV\scripts`.

The hosted Gate and the nightly queue are unchanged by the ladder: a guest run is local evidence and never Gate evidence. There is no macOS evidence source while [ADR 0097](../adr/0097-defer-the-macos-platform-indefinitely-and-deliver-windows-only.md) holds.

## Local debug artifacts

`e2e:debug` and `e2e:repeat` may emit the complete error and `cause` chain, stack, product stdout/stderr, and a failure screenshot on the developer host. Those artifacts are written only under ignored `test-results/` and never enter the repository, CI logs, or uploaded artifacts; E2E inputs remain public synthetic material or admitted Public SampleBooks, except J-01's `doc-manuscript` scenario where the local-only `.doc` is held (ADR 0079 §5, [ADR 0084](../adr/0084-admit-the-legacy-doc-to-the-background-test-guests-for-j-01.md)): its artifacts may render that manuscript's content, and an agent never opens, quotes or uploads them. For slow-renderer reproduction in J-02, J-05 and J-08, `AI7_E2E_CPU_THROTTLE=6` asks CDP to throttle renderer CPU by that factor when invoked through `e2e:debug` or `e2e:repeat`; it defaults off and ordinary Journeys and hosted CI ignore it. The debug switch is a controller-only setting that never enters the product process environment, and the `e2e`, `e2e:all`, and `e2e:diagnose` commands keep their payload-safe output byte for byte. When an agent runs them on a background test guest under ADR 0083, the artifacts stay in the guest's ignored `test-results/` and in the host's `C:\HyperV\results\<guest>\`, outside every repository.

A red Hosted Gate requires local reproduction and repair; use Draft when useful during repair. When it does not reproduce locally, the next step is reproduction in a CI-parity environment—a Windows Server 2025 virtual machine or sandbox, or a resource-constrained local run—before any diagnostic-marker Issue; marker-only changes are the last resort after that.

## Scenario admission

Every standing scenario declares its admission basis in the scenario source:

- a **supported-journey scenario** names one supported journey ID; or
- an **observed-bug regression** names the bug's GitHub issue, the user-visible outcome being preserved, and the nearest supported journey ID that supplies the complete journey around the failure.

The scenario itself is the record. Do not create a separate test catalog, coverage inventory, component-ownership matrix, or evidence registry.

A complete journey starts through the launchable AI7 product path and reaches a user-visible outcome across the applicable renderer, Electron main, AI7 service, composed Harness runtime, and domain authority boundaries. A scenario that stops at a function, module, IPC edge, service method, Harness adapter, database, package, or platform mechanic is not admitted as a standing test.

For an observed bug, add the smallest end-to-end variation of the nearest complete journey that reproduces the reported outcome. Preserve the issue link and expected outcome in the scenario. Do not build speculative edge-case catalogs, generate tests from coverage gaps or component ownership, or add cases for failures nobody has observed and no supported journey requires.

## Provider-free public-test-material boundary

The product E2E execution interval uses only public test material: runtime-generated public synthetic data, or an Owner-designated **Public SampleBook** admitted under [ADR 0043](../adr/0043-allow-public-samplebooks-in-repository-and-ci.md): exact `sample1.docx` and the four public-domain works [ADR 0091](../adr/0091-admit-four-public-domain-works-as-public-samplebooks.md) admits, each by the exact bytes `SampleBooks/README.md` lists. A Public SampleBook must be under exact root `SampleBooks/` and explicitly designated through an authorized Issue and pull request; directory placement alone is not admission. A scenario that consumes one names the exact admitted input in its own Change Brief. Under [ADR 0044](../adr/0044-use-sample1-as-compatibility-and-recording-baseline.md) and Issue #36, the current J-01 tracer consumes exact `SampleBooks/sample1.docx`, 29,550 bytes with SHA-256 `b8a3dbde0aa8a1ec7265f9ae3fe47877759e7947c5ab69682cd0a8f424a8d483`, as its standing compatibility input.

After exact dependency restoration finishes, the product subject and scenario make no live model or provider call, receive no API key or credential, perform no outbound network request, and contain no unpublished manuscript, private sample Book, or derivative of either. Public SampleBook admission does not grant provider, product-learning, export, distribution, or public-release authority; the `developer-live` transmission ADR 0091 authorizes for its four works happens outside CI and is not part of this interval. Protected development capture and necessary live validation follow ADRs 0067 and 0089 outside CI, on developer hosts only; they do not weaken this interval or require per-item attendance.

Before that interval, CI may use narrowly scoped repository checkout and declared dependency-source authentication plus approved package registries and immutable artifact sources to restore the exact committed lockfile, declared pins, and integrity-bound secondary downloads. Those infrastructure credentials never reach the product process. Any local dependency store must be reconstructable from empty. Job-local dependency caches may accelerate this step, but their initially absent state must remain supported without deleting global or shared caches. This is the declared-source-assisted bootstrap defined by the [Source Checkout Buildability Contract](./source-checkout-buildability.md), not product network access or a provider rehearsal.

A deterministic model fixture is allowed only as an in-process or local part of the same AI7 E2E journey boundary. It supplies predictable model-facing turns so the product journey can proceed; it is not a provider emulator, provider-conformance subject, replay proof, cassette programme, request-fingerprint proof, current-model-quality proof, Effect Receipt, learning input or shipped asset. J-04 consumes fixtures under `tests/fixtures/model/` through the product's in-process `ai7-local-deterministic` route, which only the J-04 launch control `--j04-model-adapter` binds. The authored synthetic fixtures' response bodies are synthetic and refer to manuscript blocks only by identity. The one admitted Recorded Deterministic Model Fixture, `sample1-recorded-v41-baseline` (Issue #387), entered after ADR 0044's normalization, sanitization, rights/content review and Issue/pull-request admission; under ADR 0079 §5 its response bodies may keep exact `sample1` free text, its provenance names the original capture, and it replays only inside the complete J-04 journey. Any further recorded fixture needs the same separate admission; raw recording bytes never enter CI or the repository.

Repository tests divide their inputs by subject, not by habit. A test whose subject is manuscript **content** — a Book outside exact `sample1`'s lineage, a revision or edit over prose, recovery of edited text, anything that reads block text back — composes its input at test time from an admitted Public SampleBook through `tests/support/composed-fixture.ts`, which excerpts the admitted file through the product's own parser and packages the excerpt; a Journey runner, which cannot import that TypeScript builder, composes the same way through `e2e/composed-docx.mjs`, its plain-JS twin, whose block positions mirror the product parser's. A test whose subject is the DOCX **container** — malformed packaging, a missing part, an import bound, a fixture whose only role is to exist — uses the generated `tests/support/synthetic-docx.ts`, and says at its call site why the container is the subject. Neither copies prose into the repository: composition reads the admitted file and writes only into a disposable test root, and a composed test speaks of its source, its block range, digests, and counts rather than of any excerpt's text, so that no failure diff, assertion message, log line, or diagnostic can carry manuscript content.

Repository test inputs may contain only clearly public synthetic material, exact Public SampleBooks admitted under ADR 0043 and ADR 0091, or an exact reviewed Recorded Deterministic Model Fixture separately admitted under ADR 0044. CI logs and uploaded build/test artifacts must not retain manuscript payloads, including Public SampleBook content or synthetic manuscript-shaped text emitted while the journey runs. Report scenario identity, state and failure location without copying editorial payloads. Public SampleBooks and deterministic model fixtures are test inputs only and never enter a shipped distribution.

## Product subject and platform contract

The E2E subject follows the launchable product path. Each hosted Windows execution begins from a fresh checkout or an equivalently empty job checkout, selects the repository-pinned toolchain, starts with empty job-local dependency-store/build-output roots, and uses the same documented root bootstrap, build, readiness, and lifecycle semantics used by developers. An optional cache may be restored only into a job-local cache root, and the first contract fulfillment on each host succeeds with that cache absent inside the same complete journey. Any Agent Data Root-owned runtime store is atomically materialized and re-verified from the declared snapshot rather than another root or a global/pre-filled store. E2E instantiates the same renderer, Electron main, service, composed Harness runtime, private IPC, required platform adapters, and non-release-only startup dependencies as local launch; only the deterministic model fixture, isolated data root, disabled outbound network, and non-substituting observation/control hooks may differ. No sibling checkout, personal path, ambient payload discovery, untracked source, pre-generated application output, private material, or CI-image-only tool is a permitted input. Build or package only as far as needed to start that subject on the current platform. A service-only, headless, topology-skipping, detached-or-immediately-exited, package-only, signing-only, or installer-only execution is not a substitute for the supported journey and does not become another gate.

Windows is the only platform that runs the supported journey IDs while [ADR 0097](../adr/0097-defer-the-macos-platform-indefinitely-and-deliver-windows-only.md) holds. The one-product rule that a resumed macOS would follow stays written: native setup and mechanics may differ for menus, shortcuts, dialogs, filesystem locations, protected secret stores, private IPC adapters, packages, signing/notarization, and OS prompts, while the supported function, domain meaning, authority transition, data outcome, and user-visible result may not differ.

There is no separate headless, packaging, signing, notarization, platform-certification, release, or same-SHA gate. Release automation may package an already accepted source state without creating new test or proof obligations.

## Observed failures and diagnostics

An admitted scenario has no quarantine, flaky registry, tolerated-failure status, or platform waiver. While the restored Gate is active, a failure or unknown on its Windows job blocks integration and is fixed in the product or scenario. During an exact pre-boundary ADR 0053 degraded interval, ADR 0054 instead makes every Windows failure or unknown blocking while a known macOS-only issue remains a truthful re-entry obligation, not a pass or tolerated failure. Remove or replace a scenario only when the supported journey or recorded bug outcome has explicitly changed; do not hide a failure behind standing exception machinery.

Hosted CI is not the development debugger. A product, bootstrap, build or Journey failure requires local reproduction and repair. Only a clearly external GitHub runner, network, or infrastructure transient may be rerun once without a code change, and only by the role responsible for that candidate under Orca dispatch. A repeated or ambiguous failure requires diagnosis before another attempt.

Keep these three repository-development states distinct:

- **Local diagnostic** uses `pnpm --silent run e2e:diagnose -- --journey <executable-admitted-id>` or an issue-bounded temporary probe to locate a concrete failure. The durable command captures child output and emits only a controller-owned Journey, closed stage identity, fixed error class, and non-completion label; it forwards no raw child output, and silent pnpm invocation does not reflect a rejected argument. Its success or failure is never completion, merge evidence, or a Gate result. Delete issue-specific probes before integration; the generic payload-safe diagnostic facility may remain. Under ADR 0062 the `e2e:debug` and `e2e:repeat` commands are also Local diagnostic: they add full-fidelity artifacts under ignored `test-results/` on the developer host without changing this payload-safe command.
- **Local completion** executes the applicable clean build and real admitted Journey path on an actual Supported Development Host and reports only source head, host, commands, and outcomes. `pnpm run e2e:all` provides the then-current executable admitted sequence when all Journeys are required, when requested by the active Issue/session; `pnpm run e2e:gate` runs only the hosted pull-request subset and is never Local completion. Resolve that sequence from `ADMITTED_JOURNEYS` at the exact candidate head, using the admission owner above. The orchestration captures and discards child streams, emits only controller-owned completion markers, stops on first failure, and claims completion only after the whole resolved set passes. An operator interruption first requests bounded cleanup of the active Journey's owned browser, loopback, and disposable runtime root, then emits a fixed interruption marker and exits nonzero; direct foreground-group signals and controller-channel loss are runner-owned cancellation inputs to the same cleanup path. A failure line `…/fail/<location>/<error-class>` is followed, when the child named one, by `…/fail/<location>/check/<label>` (Issue #652): the label the failing check was given in the runner's code, built only through `journeyCheckFailure` in `e2e/controller.mjs` and printed only when it matches `^[a-z0-9][a-z0-9-]{0,95}$`, so it never carries page, manuscript or exception text, and a unit guard (`tests/support/journey-check-labels.ts`) refuses any label a runner builds from anything but literals, loop indices, module constants, closed literal-returning helpers or its helpers' own label parameters; `run-gate.mjs`, `e2e:debug` and `e2e:repeat` print it under their own prefixes, `e2e:diagnose` does not, and the nightly queue counts it without quoting it. A child signal without a recorded controller interruption remains a failure. None is completion.
- **Hosted E2E Functional Gate** is only `.github/workflows/e2e.yml` running `GATE_JOURNEYS` on Windows for a pull request, or `.github/workflows/e2e-nightly.yml` running the admitted set on Windows — invoked for the responsible integration role or called by the existing queue, with the actual workflow target, tested tree and outcomes disclosed. The nightly invokes the same `e2e:all` orchestration a developer runs, so its log carries `LOCAL_COMPLETION/…` markers; those name the orchestrator, never the evidence class. What an occurrence is evidence of is fixed by the workflow it ran in, not by a marker prefix, and a hosted nightly is never reported as Local completion. Missing, cancelled, partial, or local results cannot be called a green Gate, and a pull-request occurrence — bounded by design under ADR 0075 — is never called full-set evidence.

CI-facing and payload-safe diagnostics never emit or retain credentials, manuscript or DOM text, IPC payload, SQL data, TypeScript error prose or source excerpts, screenshots, traces, videos, artifacts, exception messages, or arbitrary child output. The full-fidelity local debug artifacts under ADR 0062 are the only exception, and they stay inside ignored `test-results/` on the developer host or, for an agent's guest run under ADR 0083, inside the guest's ignored `test-results/` and the runner's results directories, outside every repository. Build diagnostics may expose only a bounded root-relative file/line/column/TypeScript-code tuple, a bounded `BUILD_TYPESCRIPT/config/<code>` tuple, a fixed bounded `BUILD_TYPESCRIPT/omitted/<count>` tuple, the fixed `BUILD_TYPESCRIPT/unclassified` marker, or the fixed `BUILD/unclassified` marker. The root build command enters through a fixed dynamic-import controller so implementation parse, resolution, static-import, and execution failures remain inside that boundary.

Lint, type-check, format, and build commands may exist as developer commands. The Buildability Contract requires the root build and launch semantics only because the E2E subject must be constructed from the fresh checkout; they have no independent scenario, success record, CI gate, merge evidence, coverage programme, or authority and never substitute for the E2E Functional Gate.

On the actual supported development host, normal implementation uses the repository-root sequence `doctor` → `bootstrap` → `build` → applicable Journey. Existing accepted pins and declared caches may be restored, but caches never supply correctness and a new dependency still requires exact Issue authority. The root `build` validates and replaces its canonical `dist` output, so its final run is clean. Before reporting normal Local completion, rerun `build` plus the applicable Journey. Report only the exact head, host, commands, and outcomes; do not commit logs, receipts, proof artifacts, credentials, Provider payloads, private material, personal inputs, or ambient generated output. An unavailable hosted Gate is disclosed as unavailable; local checks do not manufacture a green hosted result.

## Explicitly excluded standing gates

These exclusions govern hosted CI and merge evidence. The Owner reversed exactly two of them on 2026-09-09 through [ADR 0075](../adr/0075-split-the-hosted-gate-into-a-fast-pull-request-lane-and-a-nightly-full-gate.md) — the bar on a schedule/nightly activation path, and the bar on a bounded second lane — for that ADR's topology and nothing else. Every exclusion below stands. Unless the owner explicitly reverses ADR 0027 again, do not create separate:

- unit, integration, contract, or property test gates;
- coverage targets or coverage-driven test generation;
- lint, format, type-check, static-analysis, or architecture-closure gates;
- performance or load gates;
- security, privacy, compliance, or accessibility gates;
- provider, live-model, schema, ABI, or protocol-conformance gates;
- packaging, replay, provenance, reproducibility, signature, notarization, platform-certification, release-proof, release-receipt, or same-SHA gates; or
- formal review or exact-head review gates.

This exclusion removes separate engineering proof machinery. It does not remove AI7 product requirements, nor the developer-run Local Verification Ladder that ADR 0062 requires as a local development surface rather than a gate. Factual Verification, authority boundaries and records, Effect Receipts, recovery, privacy, accessibility, document fidelity, and long-manuscript behavior remain required product behavior and belong in a complete supported journey when that journey exercises them.

## Pull-request application

Pull-request ownership, slice correction/merge and final integration follow the current session dispatch and [Orca dispatch](./orca-dispatch.md) defaults. Update affected Journey scenarios in the same implementation slice and run the requested relevant checks. The assigned writer repairs real failures; no cross-provider Reviewer or full-ladder ceremony is required. Keep one serial integration owner and disclose unavailable hosted results without relabeling local evidence.

The active Issue's [Change Brief](change-brief.md) names the applicable journey or observed bug before implementation. Verification follows that bounded outcome; it does not expand the Issue's structural budget or create adjacent scenarios.

A testing-framework or CI-governance pull request whose Change Brief declares the Journey `N/A` validates only its bounded command, isolation, redaction, failure-propagation, workflow, and documentation contracts. It may execute an admitted real Journey to prove that the framework launches the production-shaped subject and reports the observed outcome, but that run is not Local completion for unfinished product behavior. A failure attributable to incomplete or defective product behavior stays red and is routed to its own authorized product Issue; never implement, weaken, or relabel product behavior merely to make the framework pull request pass. A failure caused by the framework itself remains inside the framework Issue and must be fixed there.
