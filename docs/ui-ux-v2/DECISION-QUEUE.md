## Issue #5 feature delta

Feature-delta Question 1/9 accepted Word-like Proposal review semantics without Word geometry: every independently reviewable change keeps an exact-range or exact-range-set anchor and persistent Manuscript-anchored Proposal Card identity; inline marks and compact margin anchors remain beside the Manuscript, only the active or nearby card expands, and large/structural work preserves the same identity through the existing virtualized navigator and Dedicated Work Workspace. No ADR was created because this selects a reversible presentation/scaling pattern over already accepted Proposal identity, long-manuscript and authority boundaries.

Feature-delta Question 2/9 accepted one Proposal Change Item per semantically independent editorial intent, with separate disposition even when adjacent items share a visual card group. Only a named Atomic Proposal Change Group may be indivisible, and only when partial acceptance would create an explicitly explained internal inconsistency; proximity, shared paragraph, Task, Run or model output is insufficient. This hard-to-reverse Proposal-decision granularity and its narrow exception are recorded in [ADR 0011](./adr/0011-use-proposal-change-items-and-explicit-atomic-groups.md).

Feature-delta Question 3/9 accepted a stable four-region Manuscript-anchored Proposal Card: `修改内容` for exact current-to-proposed content, `修改理由` for concise AI7 rationale, `依据与核查` for independently expandable source/evidence/verification records, and `你的处理` for disposition/edit controls plus the editor's optional reason. No ADR was created because the separation is a reversible information hierarchy over already distinct Proposal, evidence and decision records.

Feature-delta Question 4/9 accepted one `将以上工序保存为可复用工序` entry followed by a Reusable Procedure Classification Preview that produces exactly one Default Execution Rule, Task Skill Candidate, Workflow Profile Draft or Developer Capability Proposal. The common entry reduces terminology burden but creates no common persisted type; code-bearing needs may recommend Plugin evaluation only through the developer proposal path. No ADR was created because the underlying object and authority boundaries were already accepted and the unified entry/classification presentation is reversible.

Feature-delta Question 5/9 accepted capture from one completed Run or an explicit ordered set of completed user-visible editorial steps, with add/remove/reorder before save. The extraction preview retains reusable purpose, business structure, parameter slots and declared abstract requirements while excluding manuscript/Book/source instance content, credentials, concrete provider/model bindings, factual conclusions, decisions, approvals, receipts, hidden Harness activity and unsuccessful instance steps by default. Local provenance stays separate, and no ambient activity is captured silently. This hard-to-reverse data and authority boundary is recorded in [ADR 0012](./adr/0012-extract-reusable-structure-without-instance-authority.md).

Feature-delta Question 6/9 accepted two low-burden Task Skill save actions followed by separate authority: both create an immutable local-user candidate version; `保存并送交检查` enters AI7-owned admission and independent provider-free checking; and a successful version remains disabled until the editor reviews its Authority Ceiling and separately enables it. The authoring Run cannot validate, install, enable, approve, promote or activate its output, and repair creates a new immutable version. No ADR was created because this is the UI projection of the already accepted Task Skill admission and authority lifecycle rather than a new architecture decision.

Feature-delta Question 7/9 accepted one global Automation Center projection with typed sections, versions grouped under stable identities, exact per-version links to related work/deliveries, and manual version/entry deletion. New unpinned Task Skill use defaults to the newest enabled compatible version and freezes that exact version before authorization; existing Runs, exact rules and Workflow Instances never upgrade silently. Only a never-admitted wholly unreferenced candidate/draft may be deleted permanently; referenced or authority-bearing versions leave a non-executable Historical Version Stub and preserve all linked authoritative records, while active pins block removal. This convenience-versus-lineage decision is recorded in [ADR 0013](./adr/0013-use-latest-eligible-new-version-and-preserve-historical-pins.md).

Feature-delta Question 8/9 accepted instance-wide default discoverability for enabled local-user Task Skills through Automation Center, intent-based recommendation and manual selection. Recommendation Applicability may narrow where a skill is proactively suggested by Book, Series, Editorial Deliverable type or Workflow phase, but compatible manual selection remains possible with a mismatch explanation. Reuse carries only parameterized procedure structure, defaults every new Run Source Scope to the current Book and requires separate selection/authorization for Series, Cross-project or House Editorial Memory sources. No ADR was created because this is a reversible catalog/recommendation presentation over the already accepted separation among enablement, recommendation and per-Run source authority.

Feature-delta Question 9/9 accepted independent completion paths for the remaining classified results. Workflow Profile drafts publish as new immutable versions, and a separate action designates a version only for new Workflow Instances while existing-instance migration remains explicit. Default Execution Rule drafts require exact-envelope review before enablement and can react only to future user-submitted deterministic matches. Developer Capability Proposals are saved as non-executing developer handoffs and cannot generate, install or enable Plugins. All later edits create new versions. No ADR was created because these interactions project already accepted type, pinning, rule and developer-capability boundaries without changing their architectural ownership.

The feature-delta decision tree is closed. The two owner-requested features are fully mapped into requirements, information architecture, interaction behavior, visual direction, J-05/J-15, bilingual terms and ADRs 0011–0013 where the three-part threshold was met. This remains a candidate design package and grants no implementation authority.
