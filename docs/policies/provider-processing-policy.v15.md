# Provider Processing Policy v15

This is the human projection of [the immutable v15 JSON](provider-processing-policy.v15.json), validated by [its schema](provider-processing-policy.v15.schema.json). It directly succeeds the `ordinary-production` document [v13](provider-processing-policy.v13.json) and is written in the same schema family as developer-live [v14](provider-processing-policy.v14.md), so the launch resolver reads both the same way. Activation requires the exact [active-set v11](active-policy-set.v11.json) pin and a trusted launch that names the scope with `--trusted-operational-scope ordinary-production`; an internal active label grants no dispatch authority. Authority: [ADR 0046](../adr/0046-separate-provider-processing-by-operational-scope.md), [ADR 0048](../adr/0048-enroll-and-evaluate-background-manuscript-analysis.md), [ADR 0089](../adr/0089-adopt-orca-dispatch-and-value-first-live-model-delivery.md) and the Owner's 1.0.0 scope ([milestone scope](../development/milestone-1.0.0-scope.md)).

## In plain words

Everything v13 let the editor do with their own manuscripts, on their own computer, with their own model-service account, v15 still lets them do, and nothing more except the three things below. The editor's credential, data location, redaction, the two routes (OpenCode Go `deepseek-v4.1-flash`, the default, or the official DeepSeek platform `deepseek-flash`), the ban on the Provider Result Cache and Provider Test Ledger, and the account-limit stop are exactly v13's. See [the v13 projection](provider-processing-policy.v13.md) for those terms.

## What is newly allowed

- **Enrolled background analysis transmits, inside a mandatory ceiling.** A new eighth rule, `enrolled-background-manuscript-analysis-processing`, lets an active, matching Background Analysis Enrollment dispatch baseline manuscript analysis (`baseline-manuscript-analysis`, nothing else) as an exact Run in idle or quiet time, with no new Task each time. It is the only rule in the document that admits the background origin (`backgroundAllowed: true`, `scheduledAllowed: true`, `humanAttended: false`); the application must be running on the editor's own computer, since hosted and CI execution stay refused. v13 refused every background origin and the ordinary baseline analysis rule still does.
  - **The ceiling is mandatory.** Unlike a foreground Run, whose ceiling the editor may leave unset, an enrollment must state a tokens ceiling (`enrollmentCeilingRequired: true`, `unsetRunBudgetCeilingAllowed: false`).
  - **Series and all-Books enrollments split the ceiling equally** across the Books they schedule, the remainder going to the first Book in the scope's Book order (`ceilingSplitAcrossBooks: "equal-remainder-to-first"`).
  - **A foreground Task always keeps a slot**: background Runs hold at most the governor's capacity minus one slots (`backgroundSlotShare: "capacity-minus-one"`).
  - **Limits.** The editor's own manuscripts only through the binding they configured; manuscript analysis only (`scopeLimits`): no formal manuscript change, no external effect, no general background learning, no background policy work. A provider setup, an import or an artifact enablement never creates an enrollment, and a Default Execution Rule is not an origin here. Material References, editorial deliverables and Series Knowledge are not admitted.
- **The model may ask the editor one question per unit.** Every rule that admits a Run (baseline analysis, review, writing, the three evaluation contracts and the background rule) declares `clarification` and counts the answer turns in its bound (`transmissions.plusClarificationAnswerTurns: true`): at most one question per unit (`maxQuestionsPerUnit: 1`); that unit waits while the other units continue; after 24 hours without an answer the question counts as unanswered, the Run continues and the Run Report discloses it (`timeoutContinuesAs: "unanswered-with-run-report-disclosure"`). Editorial dialogue, 润色这段 and 稿件冲突 › 基于当前稿件重新生成建议 declare `modelQuestionAllowed: false`.
- **Review may start under its default execution rule.** The review rule now also admits a newly user-initiated Task using 审阅 快速开始 under its matching active Default Execution Rule (`matchingActiveDefaultExecutionRuleAllowed: true`). The other rules, writing included, still refuse a matching Default Execution Rule as an origin in this scope. The product controls belong to a later slice.

## What stays refused

The default is deny. Still refused: every web tool and web-bearing category (事实核查, 学术道德与引用, 出版政策与风险), **书系一致性** (Series Knowledge), a Default Execution Rule without a newly user-initiated Task, a Default Execution Rule for any rule other than review, scheduled, idle, import-triggered or cross-Run dispatch outside an active matching enrollment, background transmission of any kind but baseline analysis, hosted and CI execution, and every other task kind. Notes, internal remarks and the names and roles of the house's people are stripped first; the author's information and the house name may be sent.

## How a launch uses it

The launch resolver verifies this document byte for byte against the active-set pin and reads every rule whole, so a missing or unknown term, including a missing `clarification` or ceiling term, denies. If the editor has not yet configured a model service the projection reports `bindingState: "setup-required"` and admits no rule. Once the launch supplies the editor's configured binding, and only if it is exactly one of the two allowed bindings, all eight admitted rules, the background rule included, are filled with that route, endpoint, model and credential slot. Each projected rule carries `clarificationQuestionAllowed` and `clarificationTimeoutHours`. Provider eligibility is not Run Authorization, Apply, export, learning, publication or public release permission.
